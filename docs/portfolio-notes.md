# 기술 노트: 면접에서 설명할 판단 10가지

> ADR(`docs/decisions/`)과 `docs/progress.md`에 기록된 사실만 정리했다. 각 항목 끝에 근거 문서를 적었다.
> 형식: 문제 → 고른 방법 → 버린 대안 → 확인 방법.

## 1. 다른 임대인의 데이터: 복합 FK와 "없는 것과 같은 404"
- **문제**: 모든 화면이 `/app/leases/{id}`처럼 ID를 주소에 담는다. 조회 하나에서 `landlord_id` 조건을 빠뜨리면 다른 임대인의 세입자 개인정보가 보인다. 사람이 매번 기억하는 방식으로는 한 번의 실수를 막지 못한다.
- **고른 방법**
  - 소유 데이터 리포지토리는 `Repository<T, Long>`만 상속해 `findById`가 아예 없다. 모든 조회가 `findByIdAndLandlordId`처럼 `landlordId`를 받는다.
  - 서비스는 없는 것과 남의 것을 구분하지 않고 같은 404로 끝낸다(존재 여부를 드러내지 않음).
  - DB도 막는다. 부모에 `UNIQUE(id, landlord_id)`를 두고 자식이 `(부모_id, landlord_id)`로 참조한다. 서비스 검증을 빠뜨려도 A의 계약이 B의 호실을 가리킬 수 없다.
- **버린 대안**
  - Hibernate `@Filter`: 켜는 것을 빠뜨리면 조용히 전부 보이고, 네이티브 쿼리에는 적용되지 않는다.
  - PostgreSQL RLS: 연결마다 임대인 ID를 설정해야 해서 커넥션 풀·배치와 맞추기 번거롭다.
  - 외부용 UUID: ID를 맞히기 어렵게 할 뿐, 소유권 검증을 대신하지 못한다.
- **확인 방법**
  - `IdorTests`: 공격자가 피해자 ID로 임대인 엔드포인트 51개를 모두 호출한다. 모두 404이고, 본문·헤더가 없는 ID의 404와 같고, 소유 테이블이 바뀌지 않아야 한다.
  - 실제 매핑과 공격 표가 다르면 빌드가 실패한다(새 엔드포인트 누락 방지).
  - `OwnedRepositoryConventionTest`가 리포지토리 메서드마다 `landlordId` 인자가 있는지 검사한다.
- 근거: ADR-018

## 2. 세입자 링크 토큰: 원문은 한 번만, DB에는 SHA-256만
- **문제**: 세입자는 가입하지 않고 링크(`/t/{토큰}`)로만 들어온다. 링크가 곧 비밀번호이고 문자·카카오톡으로 오가 새어 나갈 수 있다. DB가 유출돼도 링크를 만들 수 없어야 한다.
- **고른 방법**
  - `SecureRandom` 32바이트(256비트)를 Base64URL 43자로 만들고, DB에는 SHA-256 hex만 저장한다.
  - 원문은 발급한 POST 응답 화면에 한 번만 그린다(`no-store`). flash에 넣으면 세션 저장소(DB)에 남으므로 쓰지 않는다.
  - 계약당 열린 링크는 하나(부분 UNIQUE)다. 새로고침·동시 클릭은 화면이 보던 링크 ID와 비교해 막는다.
  - 만료일은 저장하지 않고 계약의 끝 날짜 + 90일로 계산한다. 계약을 고쳐도 어긋날 수 없다.
- **버린 대안**: 원문을 암호화해 저장하고 다시 보여 주기. 편하지만 DB와 키가 함께 새면 모든 링크가 열리고, "해시만 저장" 요구와 맞지 않는다.
- **확인 방법**
  - DB·세션·flash·로그에 원문이 없는지 테스트한다.
  - 동시에 4번 눌러도 링크는 1개다.
  - 닫힌·임의·형식이 틀린·기간이 지난 토큰이 세입자 엔드포인트 8개에서 모두 같은 404다(`IdorTests` 세입자 링크 공격 표).
- 근거: ADR-026, ADR-029

## 3. `/t/**` 무세션 보안 체인과 Referrer-Policy
- **문제**: 세입자 화면에 세션 쿠키가 생기면 링크를 연 기기에 로그인 흔적이 남고, 임대인 쿠키와 섞일 수 있다. 토큰이 든 주소가 Referer로 다른 사이트에 나가도 안 된다.
- **고른 방법**
  - `/t/**`만 다루는 별도 `SecurityFilterChain`을 둔다. 세션·로그인 유지·요청 저장·CSRF 토큰을 쓰지 않는다.
  - POST는 Origin 헤더가 앱 출처와 같을 때만 받는다(null 허용 없음).
  - `Referrer-Policy: same-origin`, `X-Robots-Tag: noindex, nofollow, noarchive`, `Cache-Control: no-store`를 붙인다.
  - 세입자 화면 코드는 로그인 정보를 쓰지 않는다(ArchUnit).
- **버린 대안**: 처음에는 `no-referrer`였다. 그런데 실제 Chrome이 폼 제출의 Origin을 `null`로 보내 [입금했어요]가 403이 됐다. MockMvc 테스트는 이 동작을 재현하지 못했다. `same-origin`은 다른 사이트로는 Referer를 보내지 않으므로 목적이 그대로다. 같은 사이트 요청의 Referer에 남는 토큰은 Caddy 로그에서 가린다(7번).
- **확인 방법**
  - 실서버 테스트: 임대인 쿠키가 있어도 `/t/**` 응답에 Set-Cookie가 없다.
  - `TenantTemplateReferrerTest`: 템플릿이 이 정책을 덮어쓰지 않는다.
  - 배포 리허설(2026-10-25): 운영 구성에서 유효한 링크 200 응답에 same-origin·noindex·no-store가 있고 Set-Cookie가 없다.
- 근거: ADR-026, progress "배포 리허설"

## 4. 알림 Outbox와 `FOR UPDATE SKIP LOCKED`
- **문제**: 받을 월세 발행·입금 신고 때 알림을 보내야 한다. 서버가 죽어도 알림이 사라지면 안 되고, 같은 알림이 두 번 생기면 안 된다. 밤에 보내거나 한꺼번에 몰려 보내도 안 된다.
- **고른 방법**
  - 업무와 **같은 트랜잭션**에서 `notification` 행(PENDING)만 넣는다. `dedupe_key` UNIQUE + `ON CONFLICT DO NOTHING`이라 중복이어도 업무 트랜잭션이 깨지지 않는다.
  - 30초마다 도는 워커가 보낼 차례인 행을 `FOR UPDATE SKIP LOCKED`로 50건 잠근다. 보내기는 트랜잭션 밖에서 하고, 결과 기록은 다시 트랜잭션에서 한다.
  - 표에는 전화번호·본문·링크 원문을 저장하지 않는다. 보낼 때 만든다.
  - 발송은 09:00~20:00에만 하고, 그날 못 보내면 EXPIRED로 버린다.
- **버린 대안**
  - 커밋 직후 바로 보내기: 서버가 죽으면 알림이 사라지고, 재시도·발송 시간·이력을 다룰 곳이 없다.
  - 본문을 만들어 저장하기: 번호·링크 원문이 DB에 남고, 보낼 때 상태가 바뀌었는지 볼 수 없다.
  - 지난 날짜 따라잡기: 배치가 멈췄다 돌면 안내가 몰려 간다.
- **확인 방법**
  - 워커 2개를 동시에 돌려도 행마다 한 번만 보낸다.
  - 상태 전이표 테스트.
  - 채널을 끈 채 1주일치를 쌓고 켠 뒤 워커를 돌리면 0건이다.
  - 계약 300건이 같은 날이어도 임대인 요약 메일은 1통이다.
  - 2만 건 계획·발송 처리량을 `perfTest`로 쟀다.
  - 한계: 보낸 뒤 기록 전에 죽으면 다시 보낼 수 있다(최소 1회). 대행사 멱등 키로 막을 일로 남겼다.
- 근거: ADR-028

## 5. 입금 기록의 낙관적 락
- **문제**: 같은 받을 월세를 두 창에서 고치거나, 그사이 납부일 지남 배치·계약 종료가 같은 행을 바꿀 수 있다. 입금이 두 번 기록되면 안 된다.
- **고른 방법**
  - 폼이 보던 `version`을 숨은 칸으로 보낸다. 다르면 바로 거절한다.
  - 작업이 끝날 때 version을 정확히 1 올린다. 합계가 바뀌지 않는 작업(메모만 고침)도 `PESSIMISTIC_FORCE_INCREMENT`로 올린다.
  - 충돌하면 입력을 자동으로 다시 보내지 않고, 최신 상세와 안내를 보여 준다.
  - 받은 금액은 지우지 않은 입금 기록의 합계로 매번 다시 계산한다. 정정·삭제는 기록을 지우지 않고 사유와 함께 지운 표시를 한다.
- **버린 대안**
  - 비관적 락만 쓰기: 두 번째 요청이 기다렸다 성공해, 다른 창에서 이미 기록한 것을 모른 채 입금을 두 번 기록하게 된다.
  - 충돌 때 자동 재전송: 같은 입금이 두 번 들어갈 수 있다.
- **확인 방법**: 동시 요청 테스트(`PaymentTests`, `ExecutorService` + `CountDownLatch`)와 계약 종료·입금이 겹치는 경우의 테스트(`LeaseEndConflictTests`: 500이 아니라 다시 눌러 달라는 안내). 모든 돈 변경은 입금 기록·상태 이력·항목 이력 중 하나 이상에 남는다.
- 근거: ADR-025

## 6. 개인정보 컬럼 암호화: AES-256-GCM과 AAD
- **문제**: DB 백업이나 DB 계정이 새도 세입자 이름·연락처·계좌번호가 바로 읽히면 안 된다. 같은 번호의 세입자 중복 확인은 해야 한다.
- **고른 방법**
  - 값마다 새 IV(12바이트)를 쓰는 AES-256-GCM. 저장 형식은 `v{키버전}:{base64url}`이라 키를 바꿔도 예전 값을 읽는다.
  - 컬럼마다 용도 문자열(예: `tenant.phone`)을 AAD로 묶는다. 암호문을 다른 컬럼에 옮겨 붙이면 복호화가 실패한다.
  - 전화번호는 HMAC-SHA256을 따로 저장해 중복 확인에만 쓴다.
  - 엔티티 필드의 `toString()`은 가린 값을 낸다. 키가 없으면 local에서도 기동하지 않는다(임시 키로 저장한 데이터를 재시작 뒤 못 읽는 일을 막음).
- **버린 대안**
  - pgcrypto: 쿼리에 키가 실려 로그·통계에 남을 수 있다.
  - 같은 값 → 같은 암호문: 같은 이름·번호인지가 드러난다.
  - AES-CBC + HMAC: GCM이 암호화와 변조 감지를 한 번에 한다.
- **확인 방법**
  - 키 교체 뒤 예전 값 읽기와 컨버터 주입 테스트.
  - 배포 리허설에서 암호화 백업을 새 DB에 복구한 뒤 같은 키로 띄운 앱의 계약 화면이 원본과 같았다. DB의 이름 칸은 모두 `v1:` 암호문이었다.
- 근거: ADR-017, runbook 7

## 7. 프록시 뒤 클라이언트 IP: Caddy 주소 하나만 믿기
- **문제**: 로그인·세입자 링크 레이트 리미트를 IP로 센다. 리버스 프록시 뒤에서는 모든 요청이 프록시 IP로 보여 전체 사용자가 한 통에 묶인다. 반대로 X-Forwarded-For를 아무 데서나 믿으면 IP를 꾸며 한도를 피할 수 있다.
- **고른 방법**
  - `forward-headers-strategy: native`(Tomcat RemoteIpValve)를 쓴다. `internal-proxies`는 compose가 Caddy에 준 고정 주소 `172.30.0.10` 하나뿐이다(기본값은 사설망 전체).
  - Caddy는 밖에서 온 X-Forwarded-*를 믿지 않고 실제 접속 IP를 새로 적는다.
  - 앱 코드는 `getRemoteAddr`만 쓴다.
- **버린 대안**: 기본 신뢰 범위(사설망 전체). 같은 네트워크의 다른 컨테이너가 꾸민 헤더까지 믿게 된다.
- **확인 방법**
  - `ForwardedHeadersRealServerTests`: 신뢰 프록시의 XFF는 IP별로 따로 세고, 다른 출발지의 XFF·https는 무시한다.
  - `DeploymentFilesTest`: compose의 Caddy 주소와 앱 설정이 같다.
  - 배포 리허설: 레이트 리미트 키에 Caddy 주소가 아닌 요청 출발지가 기록됐다. 밖에서 꾸민 XFF와 내부 다른 컨테이너가 보낸 XFF는 모두 무시됐다.
- 근거: ADR-030, ADR-012

## 8. Caddy 로그에서 토큰 가리기
- **문제**: 세입자 링크 토큰은 요청 주소와(같은 사이트 요청의) Referer 헤더에 들어간다. 접근 로그가 그대로 남으면 로그를 보는 사람이 링크를 쓸 수 있다.
- **고른 방법**: Caddy `format filter`로 `request>uri`와 `Referer`의 `/t/{토큰}`을 `/t/***`로 바꾸고, Cookie·Authorization·Set-Cookie를 지운다. 접근 로그와 **기본 로거(프록시 오류 로그)** 둘 다에 같은 규칙을 둔다.
- **버린 대안**: 처음에는 접근 로그만 가렸다. 로컬 Caddy로 확인하다 앱이 응답하지 않을 때(502)의 오류 로그에 토큰이 그대로 남는 것을 찾아, 기본 로거에도 넣었다.
- **확인 방법**
  - `DeploymentFilesTest`가 두 로그 모두에 규칙이 있는지 검사한다.
  - 배포 리허설: 유효한 링크·쿼리 붙은 링크·Referer·앱을 멈춘 502 요청 뒤 Caddy 로그에 토큰 글자가 0건이었고, 쿠키 헤더도 없었다.
- 근거: ADR-030, runbook 9·13

## 9. 버튼 두 번 누르기로 생긴 세션 저장 500
- **문제**: 같은 로그인 세션으로 같은 요청이 동시에 오면(버튼 두 번 누르기), 두 응답이 모두 플래시 메시지를 세션 속성 표에 처음 넣다가 기본 키가 겹쳐 한쪽이 500이 됐다(`DuplicateKeyException`, `spring_session_attributes_pk`). 데이터는 바뀌지 않았지만 사용자는 오류 화면을 본다.
- **고른 방법**: Spring Session이 제공하는 `PostgreSqlJdbcIndexedSessionRepositoryCustomizer`를 빈으로 등록해, 세션 속성 넣기를 "있으면 덮어쓰기"(`ON CONFLICT DO UPDATE`)로 바꿨다. 표·로그인·권한 동작은 그대로다.
- **버린 대안**: 그대로 두기. 데이터가 바뀌지 않고 보안 문제도 아니어서 처음에는 고칠지를 개발자 판단으로 남겼지만, 버튼 두 번 누르기로 재현되고 사용자에게 오류 화면이 보여 고쳤다.
- **확인 방법**: 같은 세션으로 동시 요청 10회(`doubleSubmitWithTheSameSessionAnswersBothWithoutError`). 고치기 전에는 실패했고, 고친 뒤 두 요청 모두 정상 리다이렉트된다.
- 근거: progress "디자인 교체 뒤 동작 확인 2건", fix/unknown-path-404 커밋 3

## 10. 기본 거부를 지키면서 없는 주소는 404로
- **문제**: 보안 설정이 `anyRequest().denyAll()`이라, 없는 주소가 로그인 전에는 로그인 화면, 로그인 뒤에는 403 "요청을 처리할 수 없어요"가 됐다. 사용자는 주소를 잘못 친 것인지 권한 문제인지 알 수 없다.
- **고른 방법**
  - 권한 검사 앞에 `UnmappedPathNotFoundFilter`를 둔다. 허용 목록(공개 경로·`/app/**`·`/signup/kakao`) **밖**이면서 처리할 컨트롤러가 없는 주소만 404로 끝낸다.
  - 기본 거부는 그대로다. 컨트롤러가 있는 주소는 권한 검사를 그대로 거친다. 컨트롤러가 있는지 판단하다 오류가 나면 원래대로 막는다.
- **버린 대안**: 기본 거부(`denyAll`)를 풀어 없는 주소를 그냥 통과시키는 방식. 허용 목록에 없는 주소는 막는다는 원칙을 지키려고 쓰지 않았다(기본 거부는 그대로 둔다는 조건).
- **확인 방법**
  - 실제 내장 Tomcat 테스트로 화면 글자까지 확인한다(MockMvc는 오류 화면 전달을 하지 않아 글자를 볼 수 없다).
  - 정적 파일·헬스 체크·카카오 로그인·로그인/로그아웃 POST·remember-me·메서드만 다른 요청(403/405)·HEAD가 그대로인지 회귀 테스트로 고정했다.
  - 필터를 빼고 같은 테스트를 돌려 달라지는 것이 없는 주소뿐인지 확인했다.
