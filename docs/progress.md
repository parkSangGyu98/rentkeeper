## 출시 전 필수 (차단 항목: 해결 전에는 운영 배포 금지)
- [ ] **클라이언트 IP 판정**: 지금 `ClientIp`는 `request.getRemoteAddr()`를 그대로 쓴다. 운영에서 Caddy 뒤에 두면 모든 요청이 프록시 IP로 보여 **전체 사용자가 같은 레이트 리미트에 묶인다**(로그인 10분 30회를 모든 사용자가 나눠 씀). M6에서 신뢰할 프록시를 정하고 `server.forward-headers-strategy`를 설정한 뒤, 프록시 뒤에서 IP별로 따로 세어지는지 확인한다. X-Forwarded-For를 아무 요청에서나 믿으면 IP 위조가 가능하므로 신뢰 범위를 함께 정한다 (ADR-012).
- [ ] **운영용 메일 발송 구현(M6)**: 없으면 prod 프로필로 앱이 기동하지 않는다 (ADR-010). M5는 알림을 Outbox에 쌓고 로그 기록용 발송기만 만든다. 실제 메일 연결은 M6로 미뤘다(M5 결정 11).
- [ ] **카카오 앱 설정**: 서비스명 확정 후 앱 이름 변경, 운영 도메인 리다이렉트 URI 등록, 어드민 키 허용 IP 등록 (ADR-014).
- [ ] **카카오 연결 해제 웹훅(M6)**: 사용자가 카카오 쪽에서 연결을 끊었을 때 알림을 받는 웹훅 (M1-c 결정 4로 M6로 미룸).
- [ ] **Caddy 접근 로그에서 `/t/{토큰}` 가리기(M6)**: 세입자 링크 주소에는 토큰 원문이 들어 있다. 앱 로그 마스킹(M4)과 별개로, Caddy 접근 로그에 남는 요청 경로도 `/t/***`처럼 가리거나 그 경로는 기록하지 않는다. `/t/**`는 Referrer-Policy가 same-origin이라 같은 사이트 요청(CSS·JS·신고 POST)의 `Referer` 헤더에도 토큰이 들어가므로, 요청 헤더를 기록한다면 `Referer`도 가린다(브라우저 확인 F1 수정). 설정 뒤 실제 접근 로그를 열어 확인한다 (M4 결정 9·추가 요구).
- [ ] **세입자 링크 레이트 리미트(M6)**: 위 "클라이언트 IP 판정"을 고치기 전에는 Caddy 뒤에서 모든 세입자가 `/t/**` 한도(IP당 1분 30회)를 나눠 쓴다. IP 판정을 고친 뒤 세입자 링크도 IP별로 따로 세어지는지 확인한다 (M4 결정 9).

## 출시 전 전문가 검토
- [ ] **동의 기록의 법적 보관 의무**: 탈퇴 후에도 consent_log를 남겨야 하는지, 남긴다면 얼마나. 지금은 파기 때 함께 지운다 (ADR-016).
- [ ] **세입자 정보 보관 기간**: 정하지 않았다(PRD 19장 5번). **지금 세입자 정보는 임대인 탈퇴 파기로만 지워진다.** 계약이 끝난 세입자의 정보를 따로 지우는 기능은 없다 (M2 결정 19).
- [ ] **[M5 · 배포 전] 세입자 안내 문자의 법적 근거**: 임대인을 대신해 세입자에게 보내는 월세 안내·납부일 안내 문자가 광고성 정보에 해당하는지, 수신 동의가 따로 필요한지, 야간(21시~다음 날 8시) 발송 제한이 적용되는지. 지금 설계는 09~20시에만 보낸다(M5 결정 3). 개발자가 판단하지 않고 전문가에게 묻는다.
- [ ] **[M5 · 배포 전] 수신 거부 안내 문구와 방법**: 문자 끝줄 "안내 문자를 그만 받으시려면 링크 화면 아래 [안내 문자 그만 받기]를 눌러 주세요."와 링크 화면의 수신 거부 방식(전화번호·080 번호 없이 링크로만)이 충분한지. 문구 초안은 `docs/notification-templates.md`(M5 커밋 4).
- [ ] **[M5 · 배포 전] 문자 대행사 위탁 고지**: 대행사에 세입자 휴대폰 번호를 넘기는 것을 개인정보처리방침의 처리 위탁에 어떻게 적을지, 임대인이 세입자에게 알려야 하는 내용이 있는지.
- [ ] **[M5 · 배포 전] 알림 이력 보관 기간**: 알림 행(받는 사람 ID·종류·결과, 본문·번호 없음)을 얼마나 둘지. 지금 계획은 1년 뒤 지우는 정리 배치(M6)다.
- [ ] **[M5 · 배포 전] 수신 거부의 범위와 유지**: 수신 거부는 임대인별 세입자 행에 저장한다. 그래서 (1) 같은 사람이 다른 임대인에게도 세입자로 등록돼 있으면 거부가 임대인마다 따로 적용되고, (2) 임대인이 연락처를 고치면 거부가 새 번호로 따라간다. 이 범위가 수신 거부 의무에 맞는지 검토한다. 자세한 확인 결과는 아래 "M5 검토 항목 (결정 필요)".
- [ ] **탈퇴 후 카카오 회원번호 보관**: 탈퇴 후 30일이 지나 연결 끊기에 실패한 카카오 회원번호를 대기 테이블(`kakao_unlink_pending`)에 보관하는 것이 적법한지, 보관 기간을 어떻게 볼지(끊기에 성공하면 바로 삭제). 쟁점: 카카오 공식 문서는 탈퇴 시 연결 끊기를 반드시 하라고 하면서, user_id도 파기 대상 개인정보라고 한다. 이 둘을 어떻게 맞출지 (ADR-015).

### M1-a에서 확정한 결정
- 이메일 컬럼: `email` 하나 + `auth_provider`(LOCAL/KAKAO), **LOCAL 계정끼리만 unique**. 앱에서 소문자 정규화 + DB CHECK로 강제 (ADR-006)
- 중복 이메일 가입 시 "이미 가입된 이메일이에요"로 안내. 계정 존재 노출 위험은 M1-b IP 레이트 리미트로 완화
- BCrypt cost 12, `{bcrypt}` 접두사(DelegatingPasswordEncoder)
- 세션 유휴 타임아웃 2시간, 쿠키 `HttpOnly`·`Secure`(로컬도 true)·`SameSite=Lax`
- 가입 직후 바로 로그인
- 가입 폼: 이메일, 비밀번호, 비밀번호 확인, 이름(호칭), 약관·처리방침 필수 동의(검증만, 기록은 M1-c)
- 흔한 비밀번호 목록은 직접 정리한 약 100개
- 세션 principal 이름은 이메일이 아니라 landlord id

### M1-a 구현 결과 메모 (2026-10-17)
- 마이그레이션: V2 `landlord`, V3 Spring Session 테이블(공식 스크립트 그대로). ADR-005~009 작성.
- 세션 설정은 `spring.session.timeout`과 `SessionCookieConfig`(CookieSerializer 빈) 한 곳에만 둔다. Boot가 MockMvc와 실제 실행에서 `server.servlet.session.*`를 다른 경로로 읽기 때문이다 (ADR-005). 실제 Tomcat 테스트는 `SessionCookieRealServerTests` 1개뿐.
- `thymeleaf-extras-springsecurity6`는 Security 7.1.1에서 `sec:authorize`·`sec:authentication`이 동작하는 것을 테스트로 확인했다 → `@ControllerAdvice` 대체는 필요 없었다.
- 기본 거부(`denyAll`) 때문에 비로그인 상태로 없는 주소에 가면 404가 아니라 로그인 화면으로 간다(로그인 상태면 403). 404 화면은 `/css/no-such.css`처럼 허용 경로 안의 없는 파일에서 보인다 (ADR-008).
- Tailwind 4.3.3 Windows 바이너리는 이 PC에서, Linux 바이너리는 CI(PR #2)에서 동작 확인.
- Windows의 `curl.exe`로 한글 폼 값을 명령줄에서 보내면 CP949로 바뀌어 Tomcat이 400을 준다. 브라우저(UTF-8)는 정상이다. curl로 시험할 때는 `%EA%B2%80`처럼 UTF-8 퍼센트 인코딩 값을 직접 넣는다.
- 확인 완료: 개발자 브라우저 확인(가입→로그인→로그아웃, 쿠키 속성, 404 화면), CI 통과, PR #2로 main 병합.

### M1-b 구현 결과 메모 (2026-10-17)
- 마이그레이션: V4 `account_token` + `landlord.email_verified_at`, V5 `login_failure`·`rate_limit_bucket`, V6 `persistent_logins`. ADR-010~013 작성.
- 개발 메일: bootRun 콘솔에서 로거 `rentkeeper.dev-mail`의 `===== [개발용 메일 - 실제로 발송되지 않음] =====` 블록에 인증·재설정·이메일 변경 링크가 찍힌다 (local 프로필 전용, ADR-010).
- 계획 대비 확인 결과:
  - `CookieTheftException`: Security 7.1.1 기본 동작은 500 → `HashingRememberMeServices`에서 잡아 로그인 화면 안내로 처리 (ADR-013).
  - 자동 로그인 후 세션 저장, Tomcat의 remember-me `SameSite=Lax` 출력: 테스트로 확인.
  - **remember-me 키를 바꿔도 기존 로그인 유지는 풀리지 않는다** (PersistentToken 방식). 모두 끊으려면 `persistent_logins`를 비운다. 키를 바꾸면 모두 무효가 된다는 처음 설명은 틀렸고 문서에는 실제 동작을 적었다 (ADR-013, .env.example).

### M1-c 확인된 것 (2026-10-17, 개발자가 실제 카카오 계정·로컬 DB로 확인)
계획 단계에서 "확인하지 못한 것"이던 항목은 모두 확인됐다. 남은 "확인할 것"은 없다.
- [x] **PKCE**: 이전에는 카카오가 지원하는지 문서로 확인하지 못했다. Security 7.1.1 기본값대로 `code_challenge`/`code_verifier`를 보내도 실제 카카오 로그인·가입·탈퇴가 모두 성공했다. 끌 필요가 없다 (ADR-014).
- [x] **재가입·재연결 시 회원번호**: 이전에는 확인하지 못했다. 탈퇴 후 같은 카카오 계정으로 재가입해도 회원번호가 같았다(계정 2개, 회원번호 1개). 연결을 끊었다가 다시 연결해도 번호가 유지된다. 그래서 ADR-015 결정 10(사용 중 계정 보호)과 회원번호 PK 설계의 전제가 맞다.
- [x] **이미 끊긴 회원을 다시 끊을 때의 응답**(검증 3): `status=400, kakaoCode=-101`이 왔다. 카카오 문서에서 -101은 "해당 앱에 카카오계정 연결이 완료되지 않은 사용자가 호출한 경우"다. **결정**: 이 응답은 "이미 끊김"으로 보고 성공으로 처리한다. 대기 행을 지우고, 같은 회원번호의 탈퇴 행에 `kakao_unlinked_at`을 채우고, 알림은 울리지 않는다. 다른 4xx는 그대로 REJECTED다. 이미 끊긴 경우와 연결된 적 없는 회원번호는 구분하지 못한다(ADR-015 결정 14).
- [x] **탈퇴 즉시 연결 끊기**: 성공했고, 대기 행은 0이었다. 탈퇴 후 같은 카카오 계정으로 재가입(B안)도 동작했다.
- [x] **30일 뒤 파기**(검증 4): 두 계정 모두 지워졌고, 연결 데이터(동의 기록 포함)도 모두 삭제됐다. 대기 행은 생기지 않았다.
- 확인 중 수정: 카카오 scope(이메일 동의항목 제외, 위 "M1-c 브라우저 확인 중 변경"), -101 처리(V12에서 COMMENT만 갱신).

### M2에서 확정한 결정 (2026-10-17 승인)
1. **호실 상태 4가지**: 공실 / 입주중 / 입주 예정 / 기간 지남. 저장하지 않고 계약에서 계산한다. "기간 지남" ACTIVE 계약과 새 ACTIVE 계약이 함께 있을 때의 "현재 계약" 정의는 ADR-019에 적고 테스트한다.
2. **기간 경계 `[)`**: 종료일 당일 이어서 입주할 수 있다. EXCLUDE 범위식은 `daterange(start_date, end_date, '[)')`. 화면 표기는 시작일 = "들어오는 날", 종료일 = "나가는 날". PRD의 `'[]'`에서 바꾼 이유는 ADR-019.
3. **실제 종료일(`ended_on`)**: 시작일 이후 ~ 오늘까지. 예정 퇴거는 종료일(end_date) 단축으로 처리한다.
4. **월세 변경**: 적용월은 이번 달 이후이고 계약 기간 안. 아직 시작하지 않은 미래 변경은 교체·취소할 수 있고, 이미 시작된 변경은 수정할 수 없다. 최초 행(시작월)은 계약 수정으로만 정정한다.
5. **금액 기준**: lease에는 금액 컬럼을 두지 않는다. `lease_rent_history`만 기준이다.
6. **연락처 중복**: 임대인 안에서 unique. 같은 번호면 "이미 등록된 세입자로 계약할까요?"로 기존 세입자를 다시 쓴다.
7. **연락처 형식**: 휴대폰(01X)만.
8. **금액 상한**: 보증금 100억 원, 월세·관리비 1억 원(PRD).
9. **암호화 대상**: 세입자 이름·연락처·메모, 계약의 계좌번호·예금주. 건물·호실·계약 메모는 평문이고, 입력칸 아래에 "주민번호·계좌번호는 적지 마세요"를 안내한다.
10. **키**: `APP_ENCRYPTION_KEY`, `APP_ENCRYPTION_KEY_VERSION`, `APP_HMAC_KEY`(PRD) + `APP_ENCRYPTION_PREVIOUS_KEYS`(복호화 전용). local도 키 필수다(없으면 기동 실패, 임시 키 금지).
11. **삭제**: 건물은 호실이 없을 때만, 호실은 계약 기록이 없을 때만 지울 수 있다. 계약은 수정으로 정정하고, 삭제는 "청구가 없을 때만" 허용한다(M2에는 청구가 없어 항상 가능).
12. **계약 수정 범위**: 세입자 정보, 보증금, 납부일, 종료일(연장·단축, 겹침 재검사), 계좌, 메모. 호실과 시작일은 수정할 수 없다.
13. **HTMX**: M2에서 도입하지 않는다. 삭제·종료는 확인 화면(GET 확인 → POST 실행)으로 한다.
14. **임대인 연락처(`landlord.phone_enc`, SET-1)**: M2에서 빼고 M5로 미룬다.
15. **Money**: A안(`long` 유지). M3 시작 때 다시 검토한다(ADR-003).
16. **QueryDSL**: 보류한다. M3 청구 목록에서 다시 판단한다 (ADR-021: OpenFeign 포크가 Hibernate 7을 지원하지만 Spring Data 지원은 best-effort).
17. **호실 유형**: 원룸·투룸·쓰리룸 이상·상가·사무실·기타.
18. `issue_days_before`는 M3, `notify_opt_out`은 M4에서 추가한다.
19. **세입자 정보 보관 기간**: 미정으로 두고 삭제 기능은 만들지 않는다(위 "출시 전 전문가 검토").
20. **입금 계좌**: 계약마다 필수. 같은 임대인(landlord_id로 한정)의 직전 계약 계좌로 미리 채운다.
21. **건물 이름**: 같은 임대인 안에서 중복 불가. `UNIQUE(landlord_id, name)` + 친절한 안내.
- 계획에서 정한 것: 복합 FK(`(부모_id, landlord_id)`)로 다른 임대인 연결을 DB에서 차단, 리포지토리는 `findById`가 없는 형태로 모든 조회에 landlordId 필수, 계약 등록은 한 화면 4구역 + 확인 화면(세션에 평문을 저장하지 않으려고), 새 테이블은 모두 landlord CASCADE라 지금 파기 배치로 함께 지워진다(모듈별 Purger 불필요, 테스트로 확인).
- 진행 방식: V13·V14는 파일을 만든 뒤 **커밋 전에 SQL 전문을 개발자에게 보여 주고 확인을 받는다.** Hibernate 7 AttributeConverter에 Spring 빈 주입이 안 되면 멈추고 알린다.

### M3에서 확정한 결정 (2026-10-18 승인)
1. **분할**: M3-a / M3-b. 각 덩어리가 끝나면 멈추고 보고한다.
2. **자동 생성 시작**: "계약 등록일 이후가 납부일인 달부터". 등록 전 달은 수동으로 만든다. 등록할 때 이번 달 납부일이 이미 지났으면, 계약 등록 확인 화면과 계약 상세에 큰 글씨와 버튼으로 "이번 달 월세는 자동으로 만들어지지 않아요. [이번 달 받을 월세 만들기]"를 안내한다.
3. **한 달 안 세입자 교체**: 두 계약 모두 청구한다. 화면에 "이 달은 두 계약 모두 청구됐어요"를 표시하고, 금액은 임대인이 수동으로 고친다.
4. **마지막 청구월**: (실제 끝 − 하루)가 속한 달. 실제 끝은 종료했으면 `ended_on`, 아니면 `end_date`.
5. **조기 종료·나가는 날 단축**: 그 뒤 달에 이미 생긴 청구 중 입금이 없는 것은 자동 취소한다. 계약 종료·수정 화면에 "이후 달 받을 월세 N건이 취소됐어요"를 안내한다. 취소된 달은 다시 만들 수 없다.
6. **발행**: 생성 직후 배치가 자동 발행한다(SCHEDULED → ISSUED, 이력 사유 "자동 발행 — 알림 발송은 M5").
7. **전이표**: 계획의 표 + 규칙 세 가지. 취소는 입금이 없을 때만, 납부일 지남 중 일부 입금은 OVERDUE 유지, TENANT_REPORTED는 납부일 지남 배치에서 제외(PRD와 다름). PAID에서 입금을 지워 일부 받음이 됐는데 납부일이 지났으면 OVERDUE가 된다(테스트로 명시).

**DBeaver 조회 SQL (M3-b, 개인정보 없이 숫자·상태만)**

-- 35~36번: 입금 기록 (지운 기록과 정정 연결 포함). 35번 뒤 같은 청구에 지우지 않은 기록이 1건이어야 한다
SELECT id, charge_id, amount, paid_on, deleted_at IS NOT NULL AS deleted, delete_reason, replaces_id
FROM payment_record ORDER BY charge_id, id;

-- 받은 금액 = 지우지 않은 입금 합계인지 (결과 0행)
SELECT c.id, c.paid_amount, coalesce(sum(p.amount) FILTER (WHERE p.deleted_at IS NULL), 0) AS sum_active
FROM charge c LEFT JOIN payment_record p ON p.charge_id = c.id
GROUP BY c.id, c.paid_amount HAVING c.paid_amount <> coalesce(sum(p.amount) FILTER (WHERE p.deleted_at IS NULL), 0);

-- 37·40번: 항목 이력
SELECT charge_id, action, item_type, label, before_amount, after_amount, actor_type, created_at
FROM charge_item_history ORDER BY charge_id, id;

## M4 (세입자 링크·대시보드)

### M4 범위 (PRD 4.6, 4.7, 9장)
- 세입자 링크: 발급·새로 만들기·닫기(임대인), `/t/{token}` 월세 안내·입금 계좌·"입금했어요" 신고, `/t/{token}/history` 최근 12개월 (TEN-1~4)
- 임대인 신고 확인(입금 기록으로 연결)·반려
- 임대인 대시보드 (DASH-1~4)와 건물별 보기
- 범위 밖: 알림 발송·수신 거부(M5, 결정 15), 납부확인서 PDF(TEN-5, P1), 일괄 입금(PAY-5, P1)

### M4에서 확정한 결정 (2026-10-23 승인)
1. **링크 발급 시점**: 계약 상세에서 임대인이 [세입자 링크 만들기]를 누를 때. 계약 등록 때 자동으로 만들지 않는다(원문을 보여 줄 기회가 그때뿐이다).
2. **링크는 만든 직후 한 번만 보인다** (개발자 변경 반영).
   - 원문은 DB·flash·세션 어디에도 넣지 않고, POST 응답 화면에 바로 그린다(`Cache-Control: no-store`). 다시 필요하면 [새 링크 만들기]를 누르고, 그러면 예전 링크는 닫힌다.
   - 발급·닫기 폼에는 **"지금 열린 링크의 ID"를 숨은 칸**으로 넣는다(열린 링크가 없으면 빈 값). POST 때 그 값이 지금 열린 링크와 같을 때만 새 링크를 만들거나 닫는다.
   - 다르면(새로고침으로 같은 POST가 다시 오거나 다른 창에서 이미 바꿈) 아무것도 바꾸지 않고 "이미 새 링크가 만들어졌어요. 방금 만든 링크는 다시 볼 수 없어요. 필요하면 새로 만들어 주세요"를 보여 준다. 그래서 새로고침해도 방금 만든 링크가 닫히지 않는다. 이 경로를 테스트로 고정한다.
   - 같은 순간 두 요청이 오면 계약 행을 잠근 뒤 비교한다. DB 부분 UNIQUE(결정 3)가 한 번 더 막는다.
3. **계약당 열린 링크는 1개**: `UNIQUE (lease_id) WHERE revoked_at IS NULL`. M5에서 바꿔야 하면 새 마이그레이션으로 푼다.
4. **만료는 저장하지 않고 계산한다**: 열린 링크는 (계약의 실제 끝 + 90일)까지 쓸 수 있다. 실제 끝은 종료했으면 `ended_on`, 아니면 `end_date`. 저장하지 않는 이유와 끝 날짜가 비어 있을 때의 계산은 ADR-026에 적고 테스트한다.
5. **세입자 화면 공개 범위**: 건물·호실 이름, 마스킹한 세입자 이름("홍\*동님"), 월세 항목·금액·납부일, 은행·계좌번호 전체(입금에 필요), 마스킹한 예금주("김\*대"), 확인된 금액. 전화번호·보증금·계약 메모·입금 기록 메모·취소한 월세는 보이지 않는다.
6. **세입자가 보는 달**: 이번 달 + 아직 다 확인되지 않은 지난 달(최대 12개월). `/t/{token}/history`는 최근 12개월(취소 제외).
7. **"입금했어요"**: 버튼 → 확인 화면("10월 월세 550,000원을 보내셨나요?") → [네, 보냈어요].
   - 금액·날짜·입금자명은 받지 않는다. 신고할 수 있는 상태는 받을 차례·일부 받음·납부일 지남이다.
   - 이미 신고한 상태면 바꾸지 않고 같은 완료 안내를 보여 준다(멱등). 다 받음·취소는 "이미 확인됐어요".
   - **반려 뒤 다시 신고할 수 있다.** 신고를 막는 제한은 두지 않는다. 임대인 상세와 대시보드에는 상태 이력(→ TENANT_REPORTED 줄 수) 기준으로 "N번째 신고"를 표시한다(개발자 보완).
8. **세입자 POST의 CSRF**: `/t/**` 전용 체인은 세션·쿠키·remember-me를 쓰지 않으므로 **CSRF 토큰은 쓰지 않는다**. 대신 POST에 `Origin` 헤더가 있으면 그 값이 `app.base-url`의 출처(scheme://host[:port])와 같을 때만 받고, 다르면 403으로 거절한다. `Origin`이 없으면(오래된 브라우저) 받는다. 요청의 Host 헤더와 비교하지 않는다(프록시 뒤에서 달라지고, 바꿔 보낼 수 있다). 이 경로의 비밀은 URL의 토큰이고, 브라우저가 자동으로 붙이는 인증 정보는 없다. **Origin `null`은 허용하지 않는다.** 처음에는 `/t/**`에 `Referrer-Policy: no-referrer`를 썼는데, 그러면 브라우저가 폼 제출의 Origin을 `null`로 보내 "입금했어요"가 403으로 막혔다(브라우저 확인 F1, 2026-10-24). 그래서 Referrer-Policy를 `same-origin`으로 바꿨다(다른 사이트로는 여전히 링크 주소를 보내지 않는다). Origin 검사는 그대로 엄격하다.
9. **레이트 리미트 (최종 규칙)**
   - **전체 한도 `TENANT_LINK_PER_IP`**: `/t/**`의 모든 요청(GET·POST, 토큰이 맞든 틀리든, 형식이 틀린 토큰 포함)을 **IP당 1분에 30회**로 센다. 넘으면 세입자용 429 화면을 보여 준다.
   - **추가 한도 `TENANT_REPORT_PER_LINK`**: "입금했어요" 신고 POST만, **열린 링크(토큰 ID)당 1시간에 5회**로 센다. 이미 신고한 상태에서 다시 누른 것(멱등 처리)도 센다. 연타와 자동 반복을 막는 용도이며, 반려 뒤 다시 신고하는 정상 흐름(결정 7)은 1시간에 5번 반려되지 않는 한 막히지 않는다.
   - 키에는 토큰 원문이나 해시를 넣지 않는다(IP, 토큰 ID만).
   - 한계: 지금 `ClientIp`는 `getRemoteAddr()`라 Caddy 뒤에서는 모든 세입자가 전체 한도를 나눠 쓴다(가용성 문제, "출시 전 필수"의 클라이언트 IP 판정에 포함). 대입 공격의 실제 방어는 256비트 토큰이고, 레이트 리미트는 보조 수단이다.
10. **신고 반려**: 사유는 필수이고 상태 이력에만 남긴다. 세입자에게는 사유를 보이지 않고 중립 문구("집주인이 아직 입금을 확인하지 못했어요. 이미 보내셨다면 집주인에게 직접 알려 주세요.")만 보여 준다. `ChargeChanges`를 거친다(ADR-025).
11. **신고 확인**: 기존 입금 기록 화면을 다시 쓴다. 금액 기본값은 남은 금액, 받은 날 기본값은 신고한 날(서울), `source=TENANT_REPORT`. 일부만 확인할 수 있다.
12. **세입자 행동의 `actor_id`**: `tenant_access_token.id`. V17에서 `charge_status_history.actor_id` 설명을 갱신한다(V16은 고치지 않는다).
13. **목록 필터 "확인 기다림" 칸을 따로 둔다** (7칸). "받을 차례"에서 세입자 신고가 빠진다.
14. **대시보드** `/app/dashboard`, `/app`은 대시보드로 보낸다.
    - 위에서부터 ① 확인 기다리는 입금 신고(N번째 신고 표시) ② 이번 달 받을 돈·받은 돈·남은 돈 ③ 납부일 지남(모든 달, 지난 일수 순) ④ 곧 끝나는 계약(실제 끝 90일 안) ⑤ 공실 수.
    - 건물 고르기는 GET `?propertyId=`. 남의 건물이면 404.
15. **수신 거부(TEN-6)·`tenant.notify_opt_out`은 M5로** (PRD M4 범위와 다름, 개발자 승인). "알림을 하나라도 발송하기 전에 반드시 구현한다"를 M5 필수 확인에 적었다.
16. **모듈**: 토큰은 `lease` 모듈, 세입자 화면은 새 모듈 `tenantlink`(→ billing, lease), 대시보드는 새 모듈 `dashboard`(→ billing, lease, property). ArchUnit 규칙에 추가한다.
- **추가 요구 (개발자)**
  - 세입자 화면(`/t/**`)은 외부 도메인 요청(CDN 글꼴·스크립트 등)이 없다. 렌더된 HTML에 외부 URL이 없는지 테스트한다.
  - 토큰 원문은 로그·flash·세션·예외 메시지 어디에도 남기지 않는다. 앱 로그의 `/t/{토큰}`은 가린다(Caddy 접근 로그는 M6, "출시 전 필수").
- **진행 방식**
  - 커밋마다 `gradlew build`(테스트 포함) 통과를 확인한 뒤 다음으로 간다.
  - V17은 커밋 전에 SQL 전문을 보여 주고 확인을 받는다.
  - M3 쪽 버그는 M4 기능 커밋과 섞지 않고 별도 `fix` 커밋으로 고친다. 어느 M3 확인 단계와 관련 있는지 아래 "M4 중 고친 M3 버그"에 한 줄 남긴다.
  - 계획과 다르게 해야 하면 멈추고 알린다.

### M5에서 확정한 결정 (2026-10-24 승인)
- **세입자 채널 (개발자 답변)**: 세입자에게는 이메일이 없으므로 휴대폰 채널(`TENANT_PHONE`)로 Outbox에 쌓는다.
  - Outbox에는 세입자 전화번호·알림 본문·링크 원문을 저장하지 않는다. 받는 사람은 세입자·계약 ID로만 가리키고, 번호 복호화와 본문·링크 생성은 발송할 때 한다. 로그 기록용 발송기도 ID·종류·결과만 남긴다.
  - 실제 발송기가 연결되지 않은 환경(특히 prod)에서는 세입자 알림을 보내지 않는다. 채널 사용 설정은 기본 꺼짐이고, 꺼져 있으면 행을 SKIPPED로 기록한다. 나중에 발송기를 연결해 켜도 과거 알림이 한꺼번에 나가지 않는 것을 테스트로 고정한다.
  - 문자 발송의 법적 근거와 수신 거부 문구는 개발자가 판단하지 않고 "출시 전 전문가 검토"의 `[M5 · 배포 전]` 항목으로 기록했다.
  - "인증된 이메일로만"은 임대인 이메일 알림에만 적용한다.
1. **모듈**: 새 `notification` 모듈(→ billing·lease·property·landlord·common). 다른 모듈은 notification을 모른다. billing은 이벤트 record(`ChargeIssuedEvent`, `TenantReportedEvent`)만 발행하고, notification이 동기 `@EventListener`로 **같은 트랜잭션에서** Outbox 행을 넣는다(PRD 4.5). ArchUnit 규칙에 추가한다.
2. **Outbox**: `notification` 테이블, `dedupe_key` UNIQUE + `INSERT … ON CONFLICT DO NOTHING`(중복이어도 업무 트랜잭션을 깨지 않음). 워커는 30초마다 `FOR UPDATE SKIP LOCKED`로 50건씩. 재시도 1분·5분·15분, 3번 실패하면 FAILED(오류는 예외 클래스 이름만). 상태 PENDING / SENDING / SENT / FAILED / SKIPPED(사유) / EXPIRED, 도메인 메서드로만 바꾸고 전이표를 테스트한다. `claimed_until`(5분)이 지난 SENDING은 다시 가져간다(최소 1회 발송).
3. **발송 시간 09:00~20:00 (서울)**: 창 밖에서 만든 행은 다음 09:00으로 미룬다. `scheduled_for`(서울 날짜) 그날 20:00까지 못 보내면 EXPIRED로 하고 다음 날 보내지 않는다(날짜가 들어간 문구가 늦게 나가는 것을 막음). 운영 알림만 시간 제한이 없다.
4. **알림 종류**
   - 세입자(TENANT_PHONE): `CHARGE_ISSUED`(받을 월세 안내, 발행 이벤트), `DUE_REMINDER`(**납부일 전날 1회**), `OVERDUE_NOTICE`(**D+1·D+7**). PRD의 "당일/전일", "D+1·3·7"에서 줄였다(독촉처럼 느껴지지 않게, 이유는 ADR-028).
   - 임대인(EMAIL, 요약만): `TENANT_REPORT_DIGEST`(입금 신고 접수, 임대인·시간당 1통), `OVERDUE_DIGEST`(납부일 지남 요약, 하루 1통), `LEASE_END_DIGEST`(계약 끝 D-90·60·30, 하루 1통).
   - 운영: `OPS_ALERT`(코드별 하루 1통).
5. **누락 복구분·TENANT_REPORTED**: 규칙은 `NotificationRules` 한 곳.
   - 받을 월세 안내는 납부일 ≥ 오늘인 청구에만 만든다(누락 복구분·지난 달 수동 생성분은 안내 없음, 12개월 복구 테스트).
   - 계획 배치는 그날 해당하는 것만 만들고 지난 날짜를 따라잡지 않는다.
   - 납부일 지남 안내는 OVERDUE에만(TENANT_REPORTED 제외), 전날 안내는 ISSUED·PARTIALLY_PAID에만.
   - 보낼 때 상태를 다시 보고, 바뀌었으면 SKIPPED(STALE).
6. **세입자 채널 스위치**: `app.notification.tenant-phone.enabled` 기본 false. 꺼져 있으면 행을 만들되 바로 SKIPPED(CHANNEL_OFF)로 둔다(dedupe 키를 차지해 켠 뒤에도 다시 나가지 않음). prod에서 켰는데 발송기가 로그 기록용이면 기동하지 않는다.
7. **알림에 넣을 세입자 링크: C안(알림 전용 링크 유형)**
   - `tenant_access_token.purpose` = LANDLORD(임대인이 직접 만든 링크) / NOTIFICATION(알림용). 계약·유형마다 열린 링크 1개(M4 결정 3 변경). 알림을 보낼 때마다 알림 링크를 새로 만들고 예전 알림 링크는 닫는다. 임대인 링크는 그대로 둔다.
   - 알림 링크는 **실제로 발송하는 시점에만** 만든다. SKIPPED 행에는 만들지 않는다. 원문은 본문에만 넣고 DB·로그·예외에 남기지 않는다.
   - `revoke_reason` = LANDLORD_CLOSED / LANDLORD_REISSUED / NOTIFICATION_ROTATED / UNKNOWN. V20 이전에 닫힌 행은 추정하지 않고 UNKNOWN으로 채운다. 부분 UNIQUE 인덱스는 V17을 고치지 않고 V20에서 지우고 다시 만든다.
   - 다른 안(보낼 때마다 새 링크·임대인 링크도 닫음 / 예전 링크 유지 / 원문 암호화 저장)과의 비교는 ADR-029.
8. **[링크 닫기]의 효력 (개발자 변경)**: 임대인이 [링크 닫기]를 누르면 두 유형을 모두 닫고, **그 계약의 알림 링크 발급을 멈춘다**(계약의 플래그 컬럼, V20). 그동안 세입자 알림은 SKIPPED(LINK_CLOSED_BY_LANDLORD)다. 임대인이 [알림 다시 켜기]를 눌러야 재개된다([새 링크 만들기]로는 재개되지 않음). 닫기 확인 화면에 이 동작을 쉬운 말로 안내한다. 테스트로 고정한다.
9. **수신 거부 (TEN-6, 첫 기능 커밋)**: **토큰이 아니라 세입자에 저장**한다(`tenant.notify_opt_out_at`, NULL=안내 받음, V18). 같은 세입자의 모든 계약에 적용되고, 알림 링크가 새 토큰으로 바뀌어도 유지된다(테스트). 세입자 화면 아래 [안내 문자 그만 받기] → `GET /t/{token}/optout` 확인 → `POST` 완료 → `POST /t/{token}/optin`([다시 받기]). Origin 검사(M4 결정 8)와 링크당 1시간 10회 한도, 멱등. 임대인은 바꿀 수 없고 계약 상세에서 볼 수만 있다. 계획할 때와 보낼 때 모두 확인한다.
10. **잘못된 링크 화면**: 예전 알림 링크·닫힌 링크·잘못된 링크는 모두 같은 화면이다(M4 51번 규칙 유지). 문구: "링크가 맞지 않거나 기간이 지났어요. 가장 최근에 받은 안내 문자의 링크를 열거나, 집주인에게 새 링크를 요청해 주세요."
11. **발송기**: 채널별 `NotificationSender`와 로그 기록용 `LoggingNotificationSender`. 로그는 `id·type·channel·recipient(TENANT:{id}/LANDLORD:{id})·result`만. 임대인 메일의 실제 구현은 M6에서 실제 메일과 함께 한다.
12. **폭주 방지**: 세입자는 계약당 하루 1통(SKIPPED DAILY_CAP, 계획 배치도 우선순위로 하나만), 임대인은 요약 메일만, 운영은 코드별 하루 1통, 워커는 회당 50건. 테스트: 계약 300건이 같은 날이어도 임대인 메일은 요약 1통.
13. **임대인 알림 설정** `/app/settings/notifications`: 알림 세 종류와 "세입자에게 안내 문자 보내기"(전체 채널 스위치와 AND). 기본 모두 켬, `notification_preference` 테이블(V21, 행이 없으면 기본값). 이메일 미인증·없음이면 SKIPPED(EMAIL_UNVERIFIED), 인증한 뒤에도 지난 것은 보내지 않는다.
14. **임대인 연락처(`landlord.phone_enc`, SET-1)**: 임대인 문자 채널이 없어 알림톡·문자 연동 때로 다시 미룬다.
15. **알림 이력** `/app/notifications`: 최근 90일, 종류·받는 사람("101호 세입자"/"나")·상태·시각. 본문은 저장하지 않으므로 보이지 않는다. 알림 행 1년 정리 배치는 M6.
16. **운영 알림**: `OutboxOpsAlertNotifier`가 ERROR 로그를 그대로 남기고 `OPS_ALERT:{code}:{날짜}` 행을 넣는다. `OPS_ALERT_EMAIL`이 비면 SKIPPED. 알림 FAILED가 생기면 `NOTIFICATION_ALERT`를 낸다.

### M5 검토 항목 (결정 필요, 지금은 고치지 않음)
- **세입자 삭제 뒤 다시 등록하면 수신 거부가 사라지는가** (코드 기준 확인, 커밋 1):
  - 임대인이 세입자를 지우는 기능은 없다(M2 결정 19). [잘못 등록한 계약 지우기]도 계약만 지우고 세입자 행은 남긴다(`LeaseChangeService.delete`).
  - 같은 휴대폰 번호로 다시 등록하면 같은 임대인의 기존 세입자 행을 다시 쓴다(`LeaseService`의 `findByLandlordIdAndPhoneHash`). 그래서 **수신 거부는 사라지지 않는다**.
  - 예외 1: 임대인이 [계약 고치기]에서 세입자 휴대폰 번호를 바꾸면 같은 행의 번호만 바뀐다(`Tenant.change`). 거부는 새 번호를 따라가고, 옛 번호로 새로 등록한 세입자는 거부가 없는 새 행이 된다.
  - 예외 2: 임대인 탈퇴 30일 뒤 파기하면 세입자 행과 함께 거부 기록도 지워진다.
  - 앞으로 세입자 삭제 기능(보관 기간 정책)을 만들면, 지운 뒤 다시 등록할 때 거부가 사라지므로 그때 다시 정한다.
- **임대인별로 따로 적용**: 세입자 행은 임대인마다 따로 있다(`uk_tenant_landlord_phone`). 같은 사람이 임대인 A·B에게 각각 등록돼 있으면 A의 링크에서 거부해도 B의 안내는 계속 간다. 임대인을 가로질러 번호로 묶는 것은 다른 임대인의 세입자 정보를 잇는 일이라 하지 않았다.
- 두 항목 모두 "출시 전 전문가 검토"의 `[M5 · 배포 전] 수신 거부의 범위와 유지`에 연결했다.

- **M5에서 넘김 (알림)**
  - 실제 메일 발송기(SMTP/SES 등)와 임대인·운영 메일 채널 연결, 도메인 SPF·DKIM·DMARC. 연결 전에는 prod가 기동하지 않는다(ADR-010, M5 결정 11).
  - 문자·알림톡 대행사 구현체와 세입자 안내 문자 켜기(`APP_NOTIFICATION_TENANT_PHONE_ENABLED`, 사업자등록·심사 뒤). 알림 ID를 대행사 멱등 키로 넘기기(최소 1회 발송 대비), 처리 위탁 고지. 켜기 전에 "출시 전 전문가 검토"의 `[M5 · 배포 전]` 항목을 끝낸다.
  - 워커 처리량: 30초에 50건(시간당 6,000건) 상한을 대행사 처리량에 맞춰 다시 정한다(ADR-028 측정).
  - 알림 행 보관 정리 배치(1년 안, 보관 기간은 전문가 검토). 운영 알림 행(임대인 없음)은 임대인 파기로 지워지지 않으므로 이 배치가 지운다.
  - `OPS_ALERT_EMAIL`을 운영 필수로 할지, 알림 FAILED·`NOTIFICATION_ALERT` 로그 감시 연결.
  - local에서 알림 계획(08:00)을 손으로 돌리는 실행기가 필요한지(지금은 테스트로만 확인).
- `docs/runbook.md` 작성. 첫 항목 후보는 "REJECTED로 계속 실패하는 카카오 연결 끊기 대기 행 정리"(카카오 콘솔에서 연결 상태 확인 → 대기 행 수동 삭제 SQL, ADR-015 "운영 절차 후보"). "이미 끊김"(400 + -101)은 이제 자동으로 성공 처리되므로, 이 절차는 그 밖의 REJECTED에만 쓴다.
- 로그 감시: `rentkeeper.ops-alert` 로거의 `KAKAO_UNLINK_ALERT`를 알림으로 연결한다.
- 카카오 연결 해제 웹훅 (위 "출시 전 필수").
- 배포 후 본인 테스트 기간에 다른 사람의 가입을 막을 방법이 필요한지 계획 단계에서 알린다.

## 기타 메모
- 포매터는 Eclipse 기본 프로필로 시작했다. 개발자의 Eclipse 포매터 XML을 받으면 `config/formatter/eclipse-formatter.xml`을 교체하고 `.\gradlew.bat spotlessApply`로 일괄 재포맷한다 (재포맷은 별도 커밋 `style:`).
  Eclipse의 Organize Imports 순서도 함께 내보내(`.importorder`) Spotless `importOrderFile(...)`로 맞추면 저장 시 import 순서가 흔들리지 않는다. 현재는 `java, javax, org, com, 기타` 순서로 임시 지정했다.
- Spotless의 Eclipse JDT 버전은 개발자 Eclipse(2025-06 = 4.36)에 맞춰 `eclipse("4.36")`으로 고정했다. Eclipse를 업그레이드하면 이 값도 함께 올린다.
- Gradle 9.8.1은 2주 규칙의 예외로 채택했다 (ADR-004).
- PowerShell 5.1에서 한글 커밋 메시지는 `-m`으로 넘기면 깨질 수 있다. UTF-8 파일로 만들어 `git commit -F <파일>`로 커밋한다.
- 커밋하지 않을 임시 파일이 working tree에 있을 때는 `git add -A` 대신 파일을 지정해서 올린다.
