# ADR-011: 1회용 토큰은 SHA-256 해시로 저장하고, 확인(GET)과 사용(POST)을 나눈다

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- 이메일 인증(24시간), 이메일 변경(24시간), 비밀번호 재설정(30분) 링크에 토큰이 들어간다.
- 토큰 원문을 DB에 그대로 두면, DB 백업이나 조회 권한이 유출됐을 때 남의 비밀번호를 재설정할 수 있다.
- 메일 보안 검사기(스팸 필터 등)는 받은 메일의 링크를 미리 열어 보기도 한다. 링크를 여는 것(GET)만으로 토큰이 소비되면 사용자가 눌렀을 때 이미 만료돼 있다.
- 같은 링크를 두 번(또는 동시에) 눌러도 한 번만 처리돼야 한다.

## 결정
1. 토큰 원문은 `SecureRandom` 32바이트 → Base64URL(43자)로 만든다. 원문은 메일 링크에만 넣는다.
2. DB(`account_token.token_hash`)에는 **SHA-256(소문자 hex 64자)만** 저장한다. 조회도 받은 원문을 해시해서 unique 인덱스로 찾는다.
   - BCrypt 같은 느린 해시를 쓰지 않는 이유: 토큰은 256비트 무작위 값이라 대입 공격이 불가능하다. 느린 해시는 비밀번호처럼 경우의 수가 적은 값에만 의미가 있다. 같은 입력이 같은 해시를 내야 인덱스로 찾을 수 있다.
3. 형식이 다른 값(길이, 문자)은 DB를 조회하지 않고 바로 거부한다.
4. **확인과 사용을 나눈다.**
   - 링크를 연 화면(GET)은 `findUsable`로 유효한지만 본다.
   - 사용자가 버튼을 눌러 제출(POST)할 때 `consume`으로 소비한다.
5. **1회용 보장**: `UPDATE account_token SET used_at = :now WHERE id = :id AND used_at IS NULL AND expires_at > :now` 한 문장으로 조건 확인과 변경을 같이 하고, 바뀐 행 수가 1일 때만 성공으로 본다. 현재 시각은 DB `now()`가 아니라 주입된 Clock 값이다(ADR-002). 동시에 8번 시도해도 1건만 성공하는 것을 테스트로 확인했다.
6. 같은 계정·같은 용도로 새 토큰을 발급하면 이전에 쓸 수 있던 토큰은 `used_at`을 채워 무효로 만든다.
7. `consume`은 호출한 쪽 트랜잭션에 참여한다. 이후 처리(비밀번호 변경 등)가 실패해 롤백되면 토큰 사용도 함께 취소되어 다시 시도할 수 있다.
8. 정리: 매일 04:00(KST) 만료 후 7일 지난 토큰을 삭제한다(`AccountTokenCleanupJob`). 7일은 "링크가 안 된다"는 문의를 확인할 수 있게 남겨 두는 기간이다. ShedLock은 M3에서 도입한다. 삭제는 두 번 돌아도 결과가 같다.
9. 토큰을 담는 객체(`IssuedToken`)의 `toString()`은 원문을 출력하지 않는다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| 원문 저장 | DB 유출 시 바로 악용된다 |
| BCrypt 해시 | 같은 입력이 매번 다른 해시가 되어 인덱스로 찾을 수 없다. 토큰처럼 엔트로피가 큰 값에는 이점이 없다 |
| HMAC(비밀키) | DB만 유출되면 SHA-256과 같은 수준으로 안전하다. 키 관리 부담만 늘어난다 |
| 용도별 테이블 분리 | 저장소·정리 작업이 셋으로 늘어난다. 용도 차이는 `purpose` + CHECK 제약으로 충분히 표현된다 |
| GET에서 바로 소비 | 메일 검사기가 링크를 미리 열면 토큰이 사라진다 |

## 결과
- 링크가 있는 화면은 "확인 → 버튼 → 완료" 2단계가 된다.
- 토큰 원문이 브라우저 주소에 남으므로, 해당 화면은 `Referrer-Policy: no-referrer`로 다른 사이트에 주소가 전달되지 않게 한다(이메일 인증·재설정 화면에서 적용).
- remember-me 토큰(ADR-013)도 같은 `SecureTokens.sha256Hex`로 해시해 저장한다.
