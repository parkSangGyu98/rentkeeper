# ADR-017: 개인정보 컬럼 암호화(AES-256-GCM)와 전화번호 HMAC, 키 관리

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- PRD 5.2: 세입자 이름·연락처·계좌번호는 애플리케이션에서 AES-256-GCM으로 암호화해 저장한다. 키 버전을 암호문에 넣고(키 교체 대비), 검색이 필요한 전화번호는 HMAC-SHA256을 따로 저장한다. 로그에는 마스킹한 값만 남긴다.
- DB 백업이나 DB 계정이 새어도 개인정보가 바로 읽히지 않게 하려는 것이다. 앱 서버와 키가 함께 털리면 막지 못한다(앱이 복호화할 수 있어야 하므로).
- M2 결정 9·10: 암호화 대상은 세입자 이름·연락처·메모, 계약의 계좌번호·예금주다. 키는 local 포함 필수다.

## 결정
1. **방식**: AES-256-GCM. 값마다 새 IV(12바이트, `SecureRandom`), 인증 태그 128비트.
   - 저장 형식: `v{키버전}:{base64url(IV ‖ 암호문 ‖ 태그)}` (예: `v1:Q2x...`). 버전을 앞에 둬서 어떤 키로 풀지 바로 안다.
   - **용도(AAD)**: 컬럼마다 정한 문자열(예: `tenant.phone`)을 AAD로 묶는다. 다른 컬럼에 암호문을 옮겨 붙이면 복호화가 실패한다.
2. **JPA 컨버터**: `EncryptedConverter<T>`(common.crypto)를 바탕으로 컬럼마다 하위 클래스를 만들어 용도를 정한다. 엔티티 필드는 `toString()`을 마스킹한 값 타입으로 둔다. 실수로 로그에 찍혀도 평문이 나가지 않게 하려는 것이다.
   - **확인함**: Hibernate 7.4(Boot 4.1.1)는 컨버터를 Spring 빈 컨테이너로 만들어 생성자에 `FieldEncryptor`를 주입한다(`EncryptedConverterInjectionTests`).
3. **전화번호 HMAC**: `HMAC-SHA256(APP_HMAC_KEY, "phone:" + 숫자만 남긴 번호)`의 소문자 hex 64자. 같은 임대인 안에서 중복 확인에만 쓴다.
   - HMAC 키를 바꾸면 모든 해시를 다시 계산해야 해서(복호화 → 재계산) **교체를 지원하지 않는다.**
4. **환경변수** (PRD 13장 + 교체용 1개)
   | 변수 | 내용 |
   |---|---|
   | `APP_ENCRYPTION_KEY` | 현재 키, Base64로 적은 32바이트 |
   | `APP_ENCRYPTION_KEY_VERSION` | 현재 키 버전, 1 이상 정수 |
   | `APP_ENCRYPTION_PREVIOUS_KEYS` | 교체 중에만. `버전:키;버전:키`, 복호화 전용 |
   | `APP_HMAC_KEY` | Base64로 적은 32바이트 이상 |
5. **키가 없거나 형식이 틀리면 local·prod 모두 기동 실패.** local에서 임시 키를 만들지 않는다. 재시작하면 그동안 저장한 데이터를 영영 못 읽게 되기 때문이다.
   - 오류 메시지에는 변수 이름과 고치는 방법만 넣는다.
   - 테스트는 `src/test/resources/config/application.yml`의 테스트 전용 가짜 키를 쓴다(비밀값 아님, CI에는 `.env`가 없다).
6. **평문이 남지 않게**
   - 암호화 오류 메시지에는 용도와 키 버전만 넣는다(평문·암호문·키 없음). 원인 예외도 종류만 남긴다.
   - `EncryptionProperties.toString()`은 키를 숨긴다.
   - 검증 오류 메시지에 입력값을 넣지 않는다. 로그에는 `Masking`(`김*수`, `010-****-5678`, `****8901`, 메모는 길이만)을 쓴다.
7. **키 생성** (Windows PowerShell 5.1): `.env.example` 주석에 적었다. `.env`에는 UTF-8로 직접 붙여 넣고 `>>`로 덧붙이지 않는다.

## 키를 잃으면
**키를 잃으면 암호화한 세입자 이름·연락처·메모와 계좌번호·예금주를 복구할 수 없다.** 같은 문장을 `.env.example`과 키 오류 메시지에도 넣었다. 운영 키는 DB 백업과 **따로** 안전한 곳에 보관한다(M6 runbook).

## 키 교체 절차
1. 새 키를 `APP_ENCRYPTION_KEY`에, 버전을 하나 올려 `APP_ENCRYPTION_KEY_VERSION`에 넣는다.
2. 옛 키를 `APP_ENCRYPTION_PREVIOUS_KEYS`에 `옛버전:옛키`로 옮긴다. 이제 새 값은 새 키로 저장되고, 옛 값도 읽힌다(테스트로 확인).
3. 재암호화 작업으로 모든 값을 새 키로 다시 저장한다. **M2에는 만들지 않는다.** 처음 교체가 필요할 때(M6 이후) 만든다.
4. 옛 키를 제거한다.

## 한계
- 같은 값도 매번 다른 암호문이 된다. 그래서 DB에서 이름으로 검색·정렬할 수 없다. 목록 정렬은 임대인 한 명 분량을 앱에서 복호화한 뒤 한다(5~30호실 규모).
- 앱 서버와 키가 함께 노출되면 보호하지 못한다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| PostgreSQL pgcrypto | 쿼리에 키를 넘겨야 해서 SQL 로그·통계에 키가 남을 수 있다 |
| AES-CBC + HMAC | GCM이 암호화와 변조 감지를 한 번에 한다 |
| 같은 값 → 같은 암호문(결정적 암호화) | 같은 이름·번호인지가 드러난다. 중복 확인은 HMAC으로 충분하다 |
| local 임시 키 | 재시작하면 로컬 데이터를 못 읽는다 |
