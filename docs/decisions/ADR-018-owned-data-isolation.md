# ADR-018: 임대인 소유 데이터 격리 (소유권 검증과 IDOR 방지)

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- PRD 5장·7.4: 임대인 소유 데이터에는 모두 `landlord_id`가 있고, 모든 조회·수정에 `landlord_id` 조건을 강제한다. 남의 리소스 ID를 넣어도 **404**를 돌려준다(존재 여부를 노출하지 않음).
- PRD 12장 필수 테스트 7: 임대인 A가 B의 건물·계약 ID로 접근하면 404.
- 사람이 매번 조건을 기억해서 넣는 방식은 한 번만 빠뜨려도 다른 임대인의 개인정보가 보인다. **빠뜨리면 컴파일·빌드가 실패하는 구조**가 필요하다.

## 결정
1. **저장소에 `findById`가 없다.** 소유 데이터 저장소는 `JpaRepository`/`CrudRepository`가 아니라 `Repository<T, Long>`을 상속하고, 필요한 메서드만 선언한다.
   - 조회는 모두 `findByIdAndLandlordId(id, landlordId)`처럼 `landlordId`를 받는다. landlordId 없이 꺼낼 방법이 아예 없다.
   - `OwnedRepositoryConventionTest`가 검사한다: CrudRepository 상속 금지, 저장·삭제·flush를 뺀 모든 메서드에 `landlordId` 인자가 있어야 한다. 인자 이름은 `-parameters` 컴파일 옵션으로 읽는다(옵션이 빠지면 이 테스트도 실패한다).
2. **서비스:** 모든 공개 메서드의 첫 인자가 `landlordId`다. 없는 것과 남의 것을 구분하지 않고 `ResourceNotFoundException`(404)으로 끝낸다.
3. **컨트롤러:** landlordId는 `@AuthenticationPrincipal LandlordPrincipal`에서만 얻는다. 폼·주소의 `landlordId` 파라미터는 바인딩하지 않는다(테스트로 확인).
   - 검증 오류가 난 요청도 먼저 소유권을 확인한다. 그래서 남의 ID면 오류 화면이 아니라 404다.
4. **DB 이중 방어 (복합 FK):** 부모에 `UNIQUE(id, landlord_id)`를 두고, 자식은 `(부모_id, landlord_id)`로 참조한다(V13·V14). 서비스 검증을 빠뜨려도 A의 호실이 B의 건물을, A의 계약이 B의 호실·세입자를 가리킬 수 없다.
5. **엔티티는 다른 엔티티를 id로만 가리킨다**(JPA 연관관계 없음). 복합 FK와 맞추기 쉽고, 모듈 경계(ADR-020)를 넘는 객체 참조가 생기지 않는다.
6. **404 응답은 하나다:** 없는 ID와 남의 ID의 응답 본문이 같은지 테스트로 비교한다.
   - **전수 테스트(`IdorTests`)**: 임대인 B가 A의 건물·호실·계약·월세 이력 ID로 소유 데이터 엔드포인트를 **모두** 호출한다. 모두 404이고, 본문이 없는 ID의 404와 같고, 피해자 데이터가 응답에 없고, 소유 테이블 5개가 한 글자도 바뀌지 않아야 한다.
   - **누락 방지**: `/app/properties`·`/app/units`·`/app/leases`로 시작하는 실제 매핑(메서드 + 경로)과 테스트 표가 정확히 같아야 한다. 새 엔드포인트를 만들고 표에 넣지 않으면 빌드가 실패한다. 남의 ID를 받지 않는 목록·새 화면·건물 만들기 3개만 따로 허용한다.
7. **파기:** 모든 소유 테이블의 `landlord_id`는 `ON DELETE CASCADE`다. 탈퇴 파기 배치의 `DELETE FROM landlord` 한 문장으로 함께 지워진다(ADR-015). 그래서 모듈별 파기 코드가 필요 없다.
   - 자식 → 부모 복합 FK는 NO ACTION이라 앱에서는 자식이 있는 부모를 지울 수 없다. 파기 때는 한 문장 안에서 모두 CASCADE되고 NO ACTION은 문장 끝에 검사하므로 막지 않는다(`LeaseSchemaTests`).
   - DB 밖 데이터(계약서 파일 등)가 생기면 그때 파기 훅을 따로 둔다.

## 중복 이름의 친절한 안내
- 건물 이름(`uk_property_landlord_name`)과 건물 안 호실 이름(`uk_unit_property_name`)이 중복되면, 제약 이름으로 도메인 예외로 바꾼다(M1 중복 가입과 같은 방식).
- 화면에는 한글 안내만 나오고 DB 예외 메시지는 나오지 않는다(테스트로 확인). 미리 조회하지 않고 저장 시 제약으로 판단하므로 동시 요청에도 맞다.

## 모듈 경계와 호실 상태
- 호실 상태(공실/입주중/입주 예정/기간 지남)는 계약에서 계산한다. 그런데 property는 lease에 기댈 수 없다(ADR-020).
- 그래서 property가 `UnitOccupancy` 인터페이스를 정하고 lease가 구현한다. 구현이 없으면 모두 공실로 본다.
- 계약 기록이 있는 호실 삭제는 미리 묻지 않고 `fk_lease_unit` 위반으로 알아낸다(property가 lease 테이블을 모르게).

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| Hibernate `@Filter`/`@TenantId`로 자동 조건 | 세션마다 켜야 하고, 켜는 것을 빠뜨리면 조용히 전부 보인다. 네이티브 쿼리에는 적용되지 않는다 |
| PostgreSQL Row Level Security | 연결마다 임대인 ID를 설정해야 한다(커넥션 풀과 맞추기 번거로움). 배치처럼 여러 임대인을 다루는 작업이 복잡해진다. 나중에 추가 방어로 검토할 수 있다 |
| 외부 노출용 UUID(public_id) | ID를 맞히기 어렵게 할 뿐, 소유권 검증을 대신하지 못한다. 404 정책과 저장소 규칙으로 충분하다 |
| 서비스에서 조회 후 `landlordId` 비교 | 비교를 빠뜨리기 쉽다. 저장소에서 아예 조건 없이 꺼낼 수 없게 하는 쪽이 안전하다 |
