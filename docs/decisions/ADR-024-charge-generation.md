# ADR-024: 청구 자동 생성과 경계 정책

- 상태: 승인됨 (M3 커밋 3, M3 결정 2·4·6·17·18·20·21)
- 날짜: 2026-10-18

## 맥락
- 임대인이 매달 직접 청구를 만들지 않도록, 계약 조건으로 "받을 월세"를 자동으로 만든다(CHG-1·2). 같은 달을 두 번 만들면 안 된다(PRD 4.4.1).
- 날짜 경계가 많다: 들어오는 달·나가는 달, 31일 납부일, 서울 자정, 배치가 며칠 못 돈 경우, 등록 전에 지난 달.

## 결정
### 언제 무엇을 만드나 (`ChargePlanner`)
- **납부일**: 계약의 받는 날. 그 달에 없으면 그 달 마지막 날(31일의 4월 → 30일, 2월 → 28·29일).
- **만들 날**: 납부일 − `issue_days_before`(0~28일, 기본 7). 다음 달 청구가 이번 달 말에 만들어질 수 있다.
- **대상 달**: 들어오는 달 ~ 마지막 청구월. 마지막 청구월은 (실제 끝 − 하루)가 속한 달이고, 실제 끝은 종료했으면 `ended_on`, 아니면 `end_date`다(결정 4). 하루도 살지 않은 계약은 청구하지 않는다.
- **등록 전 달**: 납부일이 계약 등록일(서울) 이후(당일 포함)인 달부터 자동으로 만든다(결정 2). 등록일에 이미 납부일이 지난 달은 임대인이 직접 만든다(M3-b). 화면 안내는 커밋 5에서 붙인다.
- **누락 복구**: 배치가 못 돈 날이 있어도 다음 실행에서 빠진 달을 모두 만든다. 하한은 이번 달 기준 **12개월 전 달**이다(결정 21. 오늘이 2026-10-18이면 2025-10월분부터).
- **건너뜀**: 이미 청구가 있는 달(취소 포함, 결정 8), 월세 + 관리비가 0원인 달(결정 20).
- **금액**: 그 달 이하에서 가장 최근 월세 이력. 항목은 월세(RENT)와 관리비(MAINTENANCE)이고, 0원 항목은 만들지 않는다. 과거 청구 금액은 월세 변경으로 바뀌지 않는다(PRD 12장 필수 3).

### 저장과 발행 (`ChargeIssuer`)
- 한 달치마다 청구, 항목, 항목 이력(ADD, SYSTEM), 상태 이력을 남긴다. 상태 이력의 사유는 "자동 생성", "자동 발행 — 알림 발송은 M5", "납부일 지남"이다.
- 만들자마자 발행한다(SCHEDULED → ISSUED, 결정 6). 이미 납부일이 지난 달(누락 복구)은 이어서 OVERDUE가 된다(ADR-023).

### 배치 (`ChargeGenerator`, `ChargeGenerationJob`)
- 매일 **03:00 서울**(`cron = "0 0 3 * * *", zone = "Asia/Seoul"` = UTC 전날 18:00). ShedLock `charge-generation`, lockAtMostFor 1시간, lockAtLeastFor 1분(ADR-022).
- 업무 날짜(오늘)는 앱 Clock(서울)으로 정한다. 잠금 시각은 DB의 UTC 시각이다. 둘을 섞지 않는다.
- 대상 계약 목록은 lease 모듈의 `LeaseBillingService.billableLeases`가 준다. 실제 끝이 복구 하한 달 1일보다 뒤인 계약이고, 모든 임대인이 대상이라 id 쌍만 꺼낸다.
- **계약마다 새 트랜잭션**: 계약 행을 잠그고(`lockForBilling`, `SELECT … FOR UPDATE`), 있는 달을 읽고, 빠진 달을 만든다. 한 계약이 실패해도 나머지는 계속한다.
- **멱등**: 이미 있는 달은 건너뛴다. 동시에 다른 쪽(다른 서버, 수동 생성)이 같은 달을 만들면 `uk_charge_lease_month`가 막고, 그 계약은 "중복"으로 세고 다음 실행에서 다시 본다.
- **실패 알림**: 실패한 계약이 있으면 `CHARGE_BATCH_ALERT job=generation failed=N created=N leases=N`. 건수만 남기고 개인정보는 넣지 않는다(결정 18). 실패 로그에는 계약 id와 예외 종류만 남긴다.
- billing은 lease의 엔티티·저장소를 쓰지 않는다. `LeaseBillingService`와 값 record `LeaseBillingTerms`만 쓴다(ArchUnit).

### 계약 수정·종료와의 경합 (추가 요청 c)
- 배치는 계약마다 계약 행을 `FOR UPDATE`로 잠근 뒤 조건을 읽는다. 계약 수정·종료는 계약 행을 UPDATE하므로 같은 행 잠금을 잡는다.
  - 수정·종료가 먼저 잠갔으면: 배치는 커밋을 기다린 뒤 **바뀐 조건**(줄어든 나가는 날 등)으로 계산한다. `ChargeGenerationTests.batchWaitsForConcurrentLeaseChangeAndUsesNewTerms`로 확인했다.
  - 배치가 먼저 잠갔으면: 수정·종료가 배치의 커밋을 기다린다. 그래서 "이후 달 자동 취소"(결정 5, 커밋 5)는 배치가 방금 만든 청구까지 보고 취소할 수 있다. 커밋 5에서 수정·종료 서비스가 계약 행을 **먼저 잠근 뒤** 청구를 조회하게 하고 테스트한다.
- 교착: 계약 수정은 호실 → 계약 순서로 잠그고, 배치는 계약 행만 잠근다. 서로 반대 순서로 기다리는 일이 없다.

### 처리량 (추가 요청 e, PRD 8.3: 계약 2만 건 5분)
- 측정: `gradlew perfTest` (`ChargeGenerationThroughputTests`, 일반 빌드에서는 빠진다). 개발 PC(Windows, Docker Desktop의 Testcontainers PostgreSQL 16), 2026-10-18.
- 가장 무거운 날을 만들었다: 임대인 2,000명 × 계약 10건이 모두 같은 날 청구 1건(항목 2개)을 만든다.

| 경우 | 시간 | 처리 속도 |
|---|---|---|
| 2만 건 모두 생성 | **2분 39초** | 약 126건/초 |
| 같은 날 다시 실행 (만들 것 없음) | **42초** | 약 475건/초 |

- 목표 5분의 약 53%다. 운영 서버와 DB는 이 PC와 다르므로 배포 뒤 실제 로그(`charge generation done`)로 다시 본다.
- 한계: 오래 멈췄다가 12개월을 한꺼번에 복구하면 계약마다 최대 13건을 만들어 수십 분이 걸릴 수 있다. 계약마다 트랜잭션이라 중간에 끊겨도 다음 실행이 이어서 만든다. lockAtMostFor(1시간)를 넘기면 다른 서버가 같은 작업을 시작할 수 있지만 계약 행 잠금과 UNIQUE로 결과는 같다.
- 더 빨라야 하면: 만들 것이 없는 계약은 SQL에서 미리 거르기(만들 날이 지난 달에 청구가 없는 계약만 고르기), 계약 잠금 조회를 필요한 컬럼만 읽게 바꿔 계좌 복호화 줄이기.

## 결과
- 서버가 며칠 멈춰도 다음 실행이 빠진 달을 채운다. 같은 달을 두 번 만들지 않는다(테스트: 두 번·동시 4번 실행).
- 서울 자정이 지나야 다음 날로 본다. 03:00 실행은 UTC 전날 18:00이다(테스트: 23:59:59 / 00:00:00, 02:59:59 / 03:00).
- 등록 전 납부일이 지난 달은 자동으로 생기지 않으므로 화면 안내가 꼭 있어야 한다(커밋 5).
