# ADR-026: 세입자 링크 토큰

- 상태: 승인됨 (M4 커밋 1, M4 결정 1~4·12)
- 날짜: 2026-10-23

## 맥락
- 세입자는 가입하지 않고 임대인이 보낸 링크(`/t/{토큰}`)로만 자기 계약의 받을 월세와 입금 계좌를 본다(PRD 4.7). 링크가 곧 비밀번호다.
- 링크는 문자·카카오톡으로 오가므로 새어 나갈 수 있다. 임대인이 닫거나 바꿀 수 있어야 하고, DB가 유출돼도 링크를 만들 수 없어야 한다.

## 결정
- **토큰**: `SecureTokens.newToken()` (SecureRandom 32바이트 → Base64URL 43자, 256비트). DB(`tenant_access_token`, V17)에는 SHA-256 hex만 저장한다(`uk_tenant_access_token_hash`, 형식 CHECK). 기존 계정 토큰(ADR-011)과 같은 방식이다.
- **원문은 만든 직후 한 번만 보인다**
  - `TenantLinkService.issue`가 원문을 돌려주면, 컨트롤러가 리다이렉트하지 않고 POST 응답 화면에 바로 그린다(`Cache-Control: no-store`).
  - flash에 넣으면 세션 저장소(DB)에 잠깐이라도 원문이 남으므로 쓰지 않는다. 원문을 담는 `IssuedLink`의 `toString`은 원문을 빼고, 로그·예외 메시지에도 넣지 않는다(테스트: DB·세션·flash·로그에 원문 없음).
  - 다시 보여 줄 방법이 없다. 잃어버리면 [새 링크 만들기]를 누르고, 그러면 예전 링크는 닫힌다.
- **계약당 열린 링크 하나**: `ux_tenant_access_token_open (lease_id) WHERE revoked_at IS NULL`. 새 링크를 만들면 예전 링크를 먼저 닫는다(`revoked_at`). 닫힌 링크는 다시 열지 않는다.
- **새로고침·동시 요청** (M4 결정 2)
  - 발급·닫기 폼에 화면이 보던 열린 링크 ID를 숨은 칸으로 넣는다(없으면 빈 값).
  - 서비스는 계약 행을 잠근 뒤(`lockByIdAndLandlordId`) 지금 열린 링크와 비교한다. 다르면 아무것도 바꾸지 않고 `TenantLinkStaleException`을 던진다. 화면은 "이미 새 링크가 만들어졌어요. 방금 만든 링크는 다시 볼 수 없어요. 필요하면 새로 만들어 주세요"를 보인다.
  - 그래서 응답 화면에서 새로고침해도 방금 만든 링크가 닫히지 않는다. 동시에 4번 눌러도 링크는 1개만 생긴다(테스트).
- **만료는 저장하지 않고 계산한다** (M4 결정 4)
  - 쓸 수 있는 마지막 날 = 실제 끝 + 90일 (`TenantAccessToken.usableUntil`). 그날까지는 열리고, 다음 날부터 열리지 않는다.
  - 실제 끝은 종료했으면 `lease.ended_on`, 아니면 `lease.end_date`(나가는 날)다.
  - **끝 날짜가 둘 다 없으면** 빈 값을 돌려주고, 그 링크는 쓸 수 없는 것으로 본다(닫힌 쪽으로 실패). 지금 스키마에서는 생길 수 없지만(`end_date NOT NULL`, ENDED면 `ended_on` 필수), 앞으로 "끝 없는 계약"이 생겨도 링크가 영원히 열리는 일이 없게 한다. 단위 테스트(`TenantAccessTokenTest`)로 고정했다.
  - 기간이 지나면 새 링크를 만들 수 없고, 열린 링크도 세입자가 열 수 없다(세입자 화면 확인은 M4 커밋 2).
  - **PRD와 다른 점과 이유**: PRD 5.1은 `expires_at` 컬럼을 두지만 저장하지 않았다.
    - 만료일은 계약의 나가는 날·끝난 날에서 정해지는데, 둘은 계약 수정·종료·나가는 날 단축으로 바뀐다. 저장하면 이 모든 경로에서 링크의 만료일을 함께 고쳐야 하고, 하나라도 빠뜨리면 이미 끝난 계약의 링크가 열려 있거나 아직 쓸 링크가 닫힌다.
    - 계산하면 계약 행 하나가 유일한 기준이라 어긋날 수 없다. 조회 비용은 이미 읽는 계약 행 하나라 차이가 없다.
- **소유권**: `(lease_id, landlord_id)` 복합 FK로 같은 임대인의 계약만 가리킨다. 임대인 쪽 엔드포인트(`/app/leases/{id}/tenant-link…`)는 남의 계약이면 404다(IDOR 표). 계약을 지우거나 임대인을 파기하면 링크도 CASCADE로 지워진다.
- **세입자가 한 일의 이력**: 상태 이력의 `actor_type = TENANT`, `actor_id` = 쓴 링크의 `tenant_access_token.id`(M4 결정 12, V17에서 컬럼 설명 갱신).
- **마지막으로 연 날**: 세입자가 링크를 열 때 `last_used_at`을 서울 날짜 기준 하루에 한 번만 갱신한다(GET마다 쓰기가 생기지 않게). 계약 상세에 "세입자가 마지막으로 열어 본 날"로 보인다.

## 검토한 대안
- **원문을 암호화해 저장하고 다시 보여 주기**: 임대인은 편하지만, DB와 키가 함께 새면 모든 링크가 열린다. 해시만 저장하라는 PRD 요구와도 맞지 않아 쓰지 않았다.
- **계약 등록 때 자동 발급**: 원문을 보여 줄 기회가 없어 쓰지 않았다(M4 결정 1).
- **`expires_at` 저장**: 위 "PRD와 다른 점과 이유".

## 결과
- 링크를 잃어버리면 새로 만들어야 하고, 예전 링크를 받은 세입자는 새 링크를 다시 받아야 한다.
- M5에서 알림에 링크를 넣으려면 원문이 필요하다. 알림마다 새 링크를 만들지, 열린 링크를 여러 개 허용할지(부분 UNIQUE를 새 마이그레이션으로 바꿈) M5에서 정한다. 이때 "알림용 링크 교체"와 "임대인의 직접 닫기"를 구분해야 할 수 있다(닫은 이유 컬럼은 지금 두지 않는다).
