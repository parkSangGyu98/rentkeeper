# ADR-028: 알림 Outbox·발송 시간·안내 횟수·폭주 방지

- 상태: 승인됨 (M5 커밋 2·4·5·6, M5 결정 1~6·11~13·16)
- 날짜: 2026-10-24

## 맥락
- PRD 4.5는 알림을 업무 처리와 같은 트랜잭션에서 PENDING으로 만들고 따로 보내라고 한다(Outbox). 같은 알림은 한 번만 만들어야 한다(CLAUDE.md: 알림 발송 멱등).
- M5에는 실제 외부 발송이 없다. 세입자에게는 이메일이 없어 휴대폰(문자·알림톡) 채널이 필요하지만, 문자 대행사는 사업자등록 뒤에야 쓸 수 있다.
- 받는 사람이 40~60대 세입자다. 알림이 독촉처럼 느껴지거나, 밤에 오거나, 한꺼번에 몰려 오면 안 된다.
- 개발자 조건(2026-10-24): Outbox에 전화번호·본문·링크 원문을 저장하지 않는다. 실제 발송기가 없는 환경에서는 세입자 알림을 보내지 않고, 나중에 발송기를 붙여도 과거 알림이 한꺼번에 나가지 않는다.

## 결정
- **모듈**: 새 `notification` 모듈. billing은 이벤트(`ChargeIssuedEvent`, `TenantReportedEvent`)만 발행하고, notification이 동기 `@EventListener`로 **같은 트랜잭션에서** 행을 넣는다. 다른 모듈은 notification을 모른다(ArchUnit).
- **Outbox 테이블** `notification` (V19)
  - 받는 사람은 `recipient_type` + 세입자·계약·청구 ID 또는 임대인 ID로만 가리킨다. 전화번호·주소·제목·본문·링크 원문 컬럼이 없다. 보낼 때 그때그때 복호화하고 만든다.
  - `dedupe_key` UNIQUE + `INSERT … ON CONFLICT DO NOTHING`: 중복이어도 업무 트랜잭션을 깨지 않는다. 키에는 종류·ID·날짜만 넣는다.
  - 상태 PENDING → SENDING → SENT / PENDING(재시도) / FAILED / SKIPPED(사유) / EXPIRED. 끝난 상태는 다시 바뀌지 않는다(전이표 테스트). 엔티티는 상태만 바꾸고, 행은 SQL로 넣는다.
- **워커** (`NotificationWorker`, 30초마다, ShedLock)
  - 보낼 차례인 행을 `FOR UPDATE SKIP LOCKED`로 50건 잠그고 SENDING으로 바꾼다(잠금 5분). 워커가 둘이어도 행마다 한 번(테스트).
  - 준비(트랜잭션) → 보내기(트랜잭션 밖) → 기록(트랜잭션). 보낸 뒤 SENT 기록 전에 죽으면 잠금이 만료된 뒤 다시 보낸다: **최소 1회 발송**이다. 알림 ID를 대행사의 멱등 키로 넘겨 막는다(M6).
  - 실패하면 1분·5분·15분 뒤 다시, 세 번이면 FAILED와 운영 알림(`NOTIFICATION_ALERT`). 오류는 예외 클래스 이름만 저장하고 메시지는 남기지 않는다.
  - 로그는 `id·type·channel·recipient(TENANT:{id} 등)·result`만. 로그 기록용 발송기(local 전용)도 같다.
- **발송 시간 09:00~20:00 (서울)** (`SendWindow`)
  - 20:00 뒤에 만든 알림은 다음 날(`scheduled_for`) 09:00부터 보낸다. 보내기로 한 날 20:00까지 못 보내면 EXPIRED로 버린다: "내일이 보내실 날…" 같은 날짜 문구가 하루 늦게 나가는 것보다 안 가는 편이 낫다.
  - 운영 알림만 시간 제한이 없다.
  - 야간 발송 제한의 법적 기준은 개발자가 판단하지 않고 배포 전 전문가 검토 항목에 두었다.
- **세입자 채널 기본 꺼짐** (`app.notification.tenant-phone.enabled=false`)
  - 꺼져 있으면 행을 만들 때 바로 SKIPPED(CHANNEL_OFF)로 넣는다. 이 행이 dedupe 키를 차지하고 끝난 상태라, 나중에 켜도 과거 알림은 나가지 않는다(테스트: 1주일치를 꺼진 채 쌓고 켠 뒤 워커 → 0건).
  - 보낼 때 다시 꺼져 있으면 SKIPPED. prod에서 켰는데 실제 발송기가 없거나 로그 기록용이면 기동하지 않는다(`ProdNotificationSenderGuard`).
- **알림 종류와 안내 횟수** (`NotificationRules` 한 곳)

  | 종류 | 받는 사람 | 언제 | dedupe_key |
  |---|---|---|---|
  | 받을 월세 안내 | 세입자 | 발행할 때, 납부일이 오늘 이후인 것만 | `CHARGE_ISSUED:{청구}` |
  | 납부일 전날 안내 | 세입자 | 매일 08:00 계획, 납부일 하루 전 | `DUE_REMINDER:{청구}` |
  | 납부일 지남 안내 | 세입자 | 08:00 계획, D+1·D+7, 납부일 지남만 | `OVERDUE_NOTICE:{청구}:D{n}` |
  | 입금 신고 접수 | 임대인 | 새 신고, 임대인·시간 칸마다 한 통 | `TENANT_REPORT:{임대인}:{날짜}T{시}` |
  | 납부일 지남 요약 | 임대인 | 08:00 계획, 하루 한 통 | `OVERDUE_DIGEST:{임대인}:{날짜}` |
  | 곧 끝나는 계약 | 임대인 | 08:00 계획, 나가는 날 90·60·30일 전, 하루 한 통 | `LEASE_END_DIGEST:{임대인}:{날짜}` |
  | 운영 알림 | 운영자 | 코드마다 하루 한 통 | `OPS_ALERT:{코드}:{날짜}` |

- **PRD와 다른 안내 횟수와 이유** (개발자 승인)
  - PRD는 납부일 리마인드를 "당일/전일", 납부일 지남 안내를 D+1·3·7로 적었다. **전날 1회, D+1·D+7**로 줄였다.
  - 이유: 받는 사람이 40~60대 세입자이고, 이 서비스는 임대인을 대신해 보낸다. 한 달에 문자가 4~5통 오면 독촉처럼 느껴져 임대인과 세입자의 관계를 해칠 수 있다. 당일 안내는 전날 안내와 겹치고, D+3은 D+1 직후라 "또 왔다"는 느낌이 크다. D+7은 "사정이 있으시면 편하게 연락 주세요"로 대화를 여는 마지막 안내로 남겼다.
  - 문구에는 "연체·미납·독촉"을 쓰지 않는다(테스트). 계약당 하루 1통이고, 세입자가 언제든 끌 수 있다(TEN-6).
- **누락 복구분·세입자 신고**
  - 배치가 며칠 못 돌다 지난 달 것을 한꺼번에 발행해도 납부일이 지난 것에는 안내가 없다(12개월 복구 테스트).
  - 계획 배치는 그날 해당하는 것만 만들고 지난 날짜를 따라잡지 않는다. 하루 못 돌면 그날 알림은 빠진다(몰려 나가는 것보다 낫다고 판단).
  - 납부일 지남 안내는 OVERDUE에만, 세입자가 입금했다고 알린 것(TENANT_REPORTED)은 빠진다(M3 결정 7과 같은 기준).
  - 보낼 때 상태를 다시 보고 바뀌었으면 SKIPPED(STALE). 수신 거부·알림 멈춤·임대인 설정·하루 1통도 보낼 때 다시 본다. 모두 통과해야 마지막에 알림 링크를 만든다(ADR-029).
- **폭주 방지**: 세입자는 계약당 하루 1통(계획 때 지남 > 전날, 보낼 때 같은 날 SENT가 있으면 DAILY_CAP). 임대인은 요약 메일만(계약 300건이어도 한 통, 테스트). 운영은 코드별 하루 한 통이라 알림 실패가 운영 알림을 다시 불러도 끝이 있다. 워커는 30초에 50건.
- **임대인 메일**: 사용 중 계정의 **인증한 이메일**로만. 아니면 SKIPPED(EMAIL_UNVERIFIED)이고 인증한 뒤에도 지난 알림은 보내지 않는다. 알림 설정(`notification_preference`, V21, 행이 없으면 모두 켬)을 끄면 LANDLORD_OFF. 실제 메일 발송기는 M6다(그 전까지 prod는 기동하지 않는다, ADR-010).
- **운영 알림**: `OutboxOpsAlertNotifier`가 기존 ERROR 로그를 그대로 남기고, 새 트랜잭션으로 행을 넣는다(부른 쪽이 롤백해도 남고, 넣다 실패해도 업무를 깨지 않는다). 메일에는 코드만 넣는다.
- **이력** `/app/notifications`: 최근 90일, 종류·받는 사람·상태(보내지 않은 이유)·시각. 본문은 저장하지 않아 보이지 않는다.

## 측정 (커밋 7, 개발 PC)
- 가장 무거운 날(임대인 2,000명 × 계약 10건): 세입자 알림 계획 2만 건 1분 14초, 요약 2,000건 5초. 가져가기 쿼리 5ms.
- 발송은 묶음 안에서 초당 약 119건이지만 **워커가 30초마다 50건이라 시간당 6,000건이 상한**이다. 2.2만 건은 약 3시간 40분(09:00 → 12:40쯤)이 걸린다. 발송 시간 안이라 지금은 두고, 실제 대행사의 처리량·요금이 정해지는 M6에서 묶음 크기·주기(또는 한 번에 여러 묶음)를 다시 정한다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| 커밋 뒤(AFTER_COMMIT) 바로 보내기 | 서버가 죽으면 알림이 사라진다. 재시도·발송 시간·이력을 다룰 곳이 없다 |
| 본문을 만들어 Outbox에 저장 | 전화번호·링크 원문이 DB에 남는다(개발자 조건 1). 보낼 때 상태가 바뀌었는지도 볼 수 없다 |
| 채널이 꺼져 있으면 행을 아예 만들지 않기 | 이력에 "보내지 않음"이 남지 않고, 켜는 날 그날 계획분이 정상처럼 섞인다. SKIPPED 행이 키를 차지하는 편이 "켠 뒤 과거분 0건"을 테스트로 고정하기 쉽다 |
| 지난 날짜 따라잡기 | 배치가 며칠 멈췄다 돌면 세입자에게 안내가 몰려 간다 |

## 결과
- 알림을 업무와 같은 트랜잭션에서 넣으므로 알림 행을 넣다 실패하면 발행·신고도 롤백된다. 중복은 ON CONFLICT로 실패하지 않고, 그 밖의 실패는 계약별 트랜잭션(청구 배치) 안에서 그 계약에만 영향을 준다.
- 최소 1회 발송이라 드물게 같은 알림이 두 번 갈 수 있다(대행사 멱등 키로 막을 일, M6).
- 알림 행은 임대인 파기 때 함께 지워진다. 보관 기간과 정리 배치는 M6·전문가 검토 항목이다.
