# ADR-012: 로그인 잠금, 잠금 DoS 완화, DB 레이트 리미트

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- PRD AUTH-7: 로그인 시도 제한. 결정: **계정 기준 5회 연속 실패 시 15분 잠금 + IP 레이트 리미트(DB 저장)**.
- 계정 잠금은 그 자체로 공격 수단이 된다: 공격자가 남의 이메일로 비밀번호를 5번 틀리면 주인이 로그인하지 못한다(**계정 잠금 DoS**).
- 로그인 응답이 "잠김"과 "틀림"을 구분하면(문구든 응답 시간이든) 계정이 있는지 드러난다.
- 서버를 늘려도 한도를 공유해야 하고, Redis는 MVP에서 쓰지 않는다(PRD 3.1).

## 결정

### 1. 잠금 DoS 완화: A+B+C+D (E는 MVP 이후)
| 안 | 적용 |
|---|---|
| A. 잠금 | 연속 5회 실패 → 15분 잠금. 고정 15분, 누적 연장 없음. 잠긴 동안의 실패는 세지 않는다(공격자가 잠금을 계속 연장할 수 없게). 잠금이 끝나면 다시 5번의 기회. 로그인 성공 시 기록 삭제 |
| B. 영향 범위 제한 | 잠금은 **새 비밀번호 로그인만** 막는다. 이미 로그인된 세션과 remember-me 자동 로그인은 그대로 → 피해가 "새 기기에서 15분 대기"로 줄어든다 |
| C. 본인 해제 | 비밀번호 재설정(메일 확인)을 마치면 잠금이 바로 풀린다 |
| D. IP 레이트 리미트 | 한 IP가 여러 계정을 돌아가며 잠그거나 대량 대입하는 것을 막는다 |
| E. 기기 쿠키(OWASP) | MVP 이후. 전에 성공한 기기는 잠금을 피해 가게 하는 방식 |

### 2. 응답으로 계정 상태가 드러나지 않게
- 잠김, 틀린 비밀번호, 없는 계정, 탈퇴 계정 모두 같은 `BadCredentialsException` → 같은 `/login?error` → 같은 문구("이메일 또는 비밀번호가 맞지 않아요").
- **응답 시간 균일화**: 기본 `DaoAuthenticationProvider`는 잠긴 계정을 BCrypt 비교 전에 실패시켜 응답이 빨라진다. 그래서 `LockAwareAuthenticationProvider`로 바꿨다.
  - 계정이 있으면 잠김 여부와 상관없이 **항상 BCrypt 비교를 먼저** 한다.
  - 없는 계정이면 가짜 해시로 비교한다.
  - 테스트로 BCrypt 호출 횟수(1회)를 확인한다.
- 잠긴 동안에는 맞는 비밀번호도 실패시킨다. 잠금 중에 비밀번호가 맞는지 알려 주면 잠금이 의미가 없어진다.
- 로그인 화면에는 계정 상태가 아닌 **정책만** 항상 안내한다: "비밀번호를 5번 틀리면 15분 동안 로그인이 제한돼요."
- `LockAwareAuthenticationProvider`가 유일한 `AuthenticationProvider` 빈이다. 기본 Dao 구현이 함께 등록되면 이 구현이 실패한 뒤 기본 구현이 다시 시도해 잠금이 우회된다. "잠긴 계정 + 맞는 비밀번호 = 실패" 테스트가 이를 지킨다.
- 동시 실패는 `INSERT ... ON CONFLICT DO NOTHING` 뒤 `SELECT ... FOR UPDATE`로 행을 잠그고 세어 정확히 집계한다(10건 동시 → 정확히 5에서 잠김, 테스트).
- 실패 기록(`recordFailure`)은 **별도 트랜잭션(REQUIRES_NEW)**으로 저장한다. 비밀번호 변경 화면처럼 트랜잭션 안에서 "현재 비밀번호 틀림" 예외로 롤백되는 경우에도 기록이 남아야 하기 때문이다. 같은 트랜잭션으로 두면 롤백과 함께 기록이 사라져 그 화면에서 무제한으로 비밀번호를 맞춰 볼 수 있다(M1-b 8a 구현 중 테스트로 발견).
- 비밀번호 변경 화면의 "현재 비밀번호" 실패도 같은 횟수에 더한다. 로그인한 사용자에게는 잠김을 알려 준다("15분 뒤에 다시 시도해 주세요"). 이미 계정을 가진 사람이라 계정 존재 노출 문제가 없다.

### 3. 레이트 리미트: DB 고정 창
- `rate_limit_bucket(bucket_key PK, window_started_at, hit_count, expires_at)`에 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING hit_count` 한 문장으로 센다. 창이 끝났으면 1부터 다시 센다. 동시 요청 25건 → 정확히 한도만큼 허용(테스트).
- 만료된 카운터는 10분마다 지운다. 키에 IP가 들어 있어 오래 두지 않는다.

| 대상 | 기준 | 한도 | 넘었을 때 |
|---|---|---|---|
| 로그인 시도 (POST /login) | IP | 10분에 30회 | 429 안내 화면 |
| 회원가입 (POST /signup) | IP | 1시간에 10회 | 429 안내 화면 |
| 인증 메일 재발송 | 계정 | 1시간에 3회 | "1시간에 3번까지" 안내, 메일 안 보냄 |
| 재설정 요청 (POST /password-reset) | IP | 1시간에 10회 | 429 안내 화면 |
| 재설정 요청 (POST /password-reset) | 이메일(SHA-256 키) | 1시간에 3회 | 항상 같은 안내 문구, 메일만 안 보냄 |
| 재설정 완료 (POST /password-reset/confirm) | IP | 1시간에 20회 | 429 안내 화면 |
| 세입자 링크 `/t/**` 모든 요청 (M4 결정 9, 토큰이 틀려도 센다) | IP | 1분에 30회 | 세입자용 429 화면 |
| 세입자 "입금했어요" 신고 POST (M4 결정 9, 이미 신고한 상태에서 누른 것도 센다) | 열린 링크(토큰 ID) | 1시간에 5회 | 세입자용 429 화면, 신고 안 함 |
| 세입자 안내 문자 그만 받기·다시 받기 POST (M5 결정 9, 이미 그 상태여도 센다) | 열린 링크(토큰 ID) | 1시간에 10회 | 세입자용 429 화면, 바꾸지 않음 |
| 초대 코드 입력 (이메일·카카오 가입, M6 결정 3, 맞든 틀리든 센다) | IP | 1시간에 10회 | 429 안내 화면, 가입 안 함 |
| 임시 데모 계정 만들기 (POST /demo, M6 결정 3. 동시 데모 수 상한은 따로) | IP | 1시간에 5회 | 429 안내 화면, 만들지 않음 |

- 로그인 IP 한도는 Spring Security 필터(`LoginRateLimitFilter`)에서, 나머지는 컨트롤러에서 적용한다. 필터는 빈으로 등록하지 않는다(빈이면 서블릿 필터로도 자동 등록돼 두 번 실행된다).
- IP는 `ClientIp` 한 곳에서 `getRemoteAddr()`로 읽는다.

## 알려진 한계
1. **재설정 요청의 이메일 기준 한도(1시간 3회)는 남의 재설정 기회를 소진시킬 수 있다.** 공격자가 피해자 이메일로 재설정을 3번 요청하면, 그 1시간 동안 피해자가 직접 요청해도 메일이 가지 않는다.
   - 응답은 항상 같은 안내("가입되어 있다면 메일을 보냈어요")라서 피해자는 메일이 안 온 이유를 알 수 없다.
   - 이 한도를 두는 이유: 한도가 없으면 공격자가 남의 메일함에 재설정 메일을 무제한 보낼 수 있다(메일 폭탄, 발송 비용·평판 문제). 두 위험 중 메일 폭탄을 막는 쪽을 택했다.
   - 피해는 1시간 지연으로 제한된다. 메일이 이미 가 있다면 그 안의 마지막 링크는 30분간 유효하다.
   - 운영 중 이런 신고가 생기면 한도 조정이나 CAPTCHA를 검토한다.
2. **운영에서 프록시 뒤에 두면 IP가 모두 같아진다.** Caddy 뒤에서 `getRemoteAddr()`는 프록시 IP를 돌려주므로 전체 사용자가 같은 한도에 묶인다. **출시 전 필수(차단 항목)**로 docs/progress.md에 기록했다. M6에서 신뢰할 프록시를 정하고 `server.forward-headers-strategy`를 설정한다(X-Forwarded-For를 아무 요청에서나 믿으면 IP 위조가 가능하므로 신뢰 범위를 함께 정한다).
3. 공유 IP(회사, 통신사 NAT, 모바일 CGNAT) 사용자는 함께 한도에 걸릴 수 있다. 수치를 넉넉히 잡았고 운영하며 조정한다.
4. 고정 창은 창이 바뀌는 순간 앞뒤로 한도의 최대 2배까지 몰릴 수 있다. MVP에서는 수용한다.
5. IP는 개인정보로 볼 여지가 있다. 카운터는 길어야 1시간 남고 정리 작업이 지운다. 처리방침 검토(출시 전 할 일)에 포함한다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| 잠금 없이 지연(점점 느리게)만 | 결정 사항(5회 잠금)과 다르고, 분산 공격에 약하다 |
| 잠금 시 "잠겼어요" 안내 | 계정 존재와 상태가 드러난다 |
| 메모리(Bucket4j 등) 레이트 리미트 | 서버를 늘리면 한도가 서버마다 따로 논다. 재시작하면 초기화된다 |
| Redis | MVP에서 캐시·Redis를 쓰지 않기로 했다 |
| 슬라이딩 윈도 | 정확하지만 요청마다 기록이 쌓인다. MVP 규모에서는 고정 창으로 충분하다 |
