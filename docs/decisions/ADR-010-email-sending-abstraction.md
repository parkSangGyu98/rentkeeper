# ADR-010: 메일 발송 추상화와 개발용 로그 구현의 제한

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- M1-b부터 이메일 인증·비밀번호 재설정 메일이 필요하다. 실제 발송(SMTP/SES)은 M5에서 붙인다.
- 개발 중에는 메일 대신 로그로 링크를 확인해야 한다. 그런데 그 링크에는 **인증·재설정 토큰 원문**이 들어 있다. 운영 로그에 남으면 로그를 볼 수 있는 사람 누구나 남의 비밀번호를 재설정할 수 있다.
- 메일을 DB 트랜잭션 안에서 바로 보내면, 토큰 저장이 롤백돼도 메일은 이미 나간 상태가 될 수 있다.

## 결정
1. `common/mail/EmailSender` 인터페이스(`send(EmailMessage)`)를 둔다. M5에서 실제 발송 구현을 추가한다.
2. 업무 코드는 `EmailDispatcher.sendAfterCommit(...)`만 쓴다. 발송 요청을 이벤트로 발행하고 `@TransactionalEventListener(AFTER_COMMIT)`에서 보낸다.
   - 트랜잭션이 커밋된 뒤에만 나가고, 롤백되면 나가지 않는다. 트랜잭션 밖에서 부르면 바로 보낸다.
   - 발송 실패는 오류 로그만 남기고 사용자 요청은 실패시키지 않는다(업무 처리는 이미 커밋됨). 로그에는 본문(토큰)을 넣지 않는다.
   - 발송 요청이 이벤트 한 곳에 모여 있어 M5에서 Outbox(PRD 4.5)로 옮기기 쉽다.
3. 개발용 `LoggingEmailSender`는 **`@Profile("local")`일 때만 빈으로 등록**한다. 로거 이름은 `rentkeeper.dev-mail`.
4. 운영(prod)에서는 `ProdEmailSenderGuard`가 기동할 때 확인한다.
   - `EmailSender` 구현이 없으면 기동 실패 ("운영(prod)용 메일 발송 구현(EmailSender)이 없습니다").
   - 설정 실수로 `LoggingEmailSender`가 등록돼 있어도 기동 실패.
5. `EmailMessage.toString()`은 본문을 감춘다. 실수로 객체를 로그에 찍어도 토큰이 남지 않는다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| 운영에서는 아무것도 안 하는 구현(No-op) | 사용자는 인증·재설정 메일을 영영 받지 못하는데 아무도 모른다. 실패는 조용히 숨는 것보다 바로 드러나는 편이 낫다 |
| 로그 구현을 모든 프로필에서 쓰되 토큰을 가림 | 개발 중에 링크를 쓸 수 없게 된다 |
| 트랜잭션 안에서 바로 발송 | 롤백된 토큰의 링크가 나갈 수 있다. 외부 발송이 느리면 DB 트랜잭션도 길어진다 |
| 지금 바로 Outbox 테이블 도입 | PRD상 M5 범위. 지금은 이벤트로 입구만 하나로 모아 둔다 |

## 결과
- **M5에서 실제 발송 구현을 추가하기 전에는 prod 프로필로 앱이 뜨지 않는다.** 운영 배포(M6)가 M5 뒤라서 일정에는 영향이 없다.
- 테스트는 `RecordingEmailSender`(테스트 전용, `@Primary`)로 보낸 메일을 받아 링크의 토큰을 꺼낸다.
- 로컬에서 bootRun 콘솔에 `rentkeeper.dev-mail` 로거로 `===== [개발용 메일 - 실제로 발송되지 않음] =====` 블록이 찍힌다. 링크는 이 블록 안에 있다.
