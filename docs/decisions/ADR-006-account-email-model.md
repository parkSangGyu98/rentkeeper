# ADR-006: 계정 이메일 모델 — 정규화와 공급자별 유일성

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- 가입 방식이 두 가지다: 이메일+비밀번호(M1-a), 카카오 로그인(M1-c).
- 결정 사항: **같은 이메일이어도 계정을 자동으로 합치지 않는다.** 카카오 계정이 동의한 이메일(또는 직접 입력한 알림 이메일)이 기존 이메일 가입 계정과 같을 수 있다.
- 사용자는 이메일을 `Kim@Example.com`처럼 대소문자를 섞어 입력하기도 한다. 대소문자만 다른 주소로 두 번 가입되면 안 된다.
- 알림은 인증된 이메일로만 보낸다(M1-b).

## 결정
1. `landlord.email` 컬럼 하나를 둔다. 의미는 "이 계정의 연락·알림 이메일"이며, 이메일 가입(LOCAL) 계정에서는 로그인 ID를 겸한다.
2. `landlord.auth_provider`(`LOCAL`/`KAKAO`)를 추가한다 (PRD 5.1에는 없던 컬럼).
3. 유일성은 **LOCAL 계정끼리만** 건다: `CREATE UNIQUE INDEX uk_landlord_local_email ON landlord (email) WHERE auth_provider = 'LOCAL'`. 카카오 계정의 유일성은 M1-c의 `kakao_id`로 건다.
4. 이메일은 **앱에서 정규화**한다: 앞뒤 공백 제거 + `toLowerCase(Locale.ROOT)`. 정규화는 `EmailAddress` 값 객체에서만 하고, 가입·로그인 모두 이 타입을 거친다.
5. DB가 한 번 더 막는다: `CHECK (email = lower(btrim(email)))`. 정규화를 빠뜨린 코드가 생겨도 저장이 실패한다.
6. 국제화 이메일(한글 주소 등)은 받지 않고 ASCII로 제한한다. Java와 PostgreSQL의 소문자 변환 규칙이 비ASCII 문자에서 다를 수 있어 5번 제약과 어긋날 위험이 있기 때문이다.
7. 존재 확인 후 INSERT 사이에 같은 이메일 가입이 끼어들면 DB unique 위반이 난다. 위반된 제약 이름이 `uk_landlord_local_email`일 때만 `DuplicateEmailException`으로 바꾸고, 다른 제약 위반은 그대로 올린다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| 전체 계정에 `email` unique | 카카오 계정이 같은 이메일을 쓰면 가입 자체가 막힌다 → 자동 병합 금지 결정과 충돌 |
| `login_email`과 `notification_email` 분리 | 개념은 분명하지만 LOCAL 계정은 같은 값을 두 번 저장하고, 인증 상태도 두 곳에서 관리해야 한다 |
| `lower(email)` 함수 인덱스, 원문 저장 | 모든 조회에 `lower()`를 빠짐없이 써야 한다. 한 곳만 빠져도 중복 확인이 뚫리거나 인덱스를 못 쓴다 |
| `citext` 확장 | 확장 하나 추가와 JPA 타입 매핑 문제가 생긴다. 정규화 + CHECK로 같은 효과를 얻는다 |
| Gmail 점·`+태그` 제거 | 메일 서비스마다 규칙이 달라 추측이 된다. 하지 않는다 |

## 결과
- 로그인할 때도 같은 정규화를 거치므로 대문자로 입력해도 로그인된다.
- 중복 가입 시 "이미 가입된 이메일이에요"로 안내한다. 계정 존재 여부가 노출되는 위험은 M1-b의 IP 레이트 리미트로 완화한다.
- M1-c에서 탈퇴 유예 기간(30일) 중 재가입 정책이 정해지면 `uk_landlord_local_email`의 조건(예: `AND status = 'ACTIVE'`)만 다시 만들면 된다.
