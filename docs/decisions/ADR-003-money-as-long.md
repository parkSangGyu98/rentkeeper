# ADR-003: 금액은 원 단위 정수(long / bigint)로 저장한다

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- 다루는 금액은 원화(KRW) 월세·관리비·공과금이며, 원화에는 실사용 소수 단위가 없다.
- 입력 범위는 0 이상, 항목당 최대 1억 원(PRD 4.3). 연간 합계도 수십억 원 수준이다.
- 금액 오류는 서비스 신뢰에 치명적이므로 표현 방식에서 오차 가능성을 없애야 한다.

## 결정
- 자바: `long`(원). DB: `bigint`. 화면 표시 시에만 천 단위 구분 기호로 포맷한다.
- `float` / `double`은 금액에 절대 쓰지 않는다.
- 금액 입력 검증(0 이상, 1억 이하)은 도메인 계층에서 수행하고, DB에도 `CHECK` 제약을 건다(해당 테이블을 만드는 마일스톤에서).

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| `double` | 이진 부동소수점이라 `0.1 + 0.2 != 0.3` 같은 오차가 생긴다 |
| `BigDecimal` / `numeric` | 정확하지만, 소수가 없는 원화에는 과하다. 불변 객체 연산이 장황하고 `equals`가 scale을 비교해(`1.0` ≠ `1.00`) 실수 여지가 있다 |
| `Money` 값 객체 (+ 통화) | 다통화는 비목표(다국어·해외 없음). 필요해지면 `long`을 감싸는 값 객체로 무리 없이 전환 가능 |

## 결과
- `long` 최대값(약 9.2 × 10^18)은 요구 범위보다 압도적으로 커서 오버플로 위험이 사실상 없다. 그래도 합계 계산에는 `Math.addExact`를 써서 이상 입력을 조기에 드러낸다.
- 일할 계산·부가세처럼 나눗셈이 생기는 기능(현재 MVP 비지원)을 도입할 때는 **반올림 정책(버림/반올림/올림)을 별도 ADR로 먼저 정한다.**
