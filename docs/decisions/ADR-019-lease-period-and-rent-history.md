# ADR-019: 계약 기간 경계([)), 겹침 차단, 호실 상태, 월세 이력

- 상태: 승인됨
- 날짜: 2026-10-17

## 맥락
- PRD LEASE-4: 호실당 활성 계약 1개. 기간이 겹치는 활성 계약은 등록할 수 없다(DB + 서비스 검증). PRD 5.1은 `daterange(start_date, end_date, '[]')`였다.
- PRD PROP-3: 호실 상태(공실/입주중)는 계약 유무로 자동 계산한다. M2 결정 1에서 4가지(공실/입주중/입주 예정/기간 지남)로 늘렸다.
- PRD LEASE-2: 월세를 바꾸면 이력을 남기고 적용 시작 월을 정한다. 과거 청구는 바꾸지 않는다.

## 결정
1. **기간은 `[들어오는 날, 나가는 날)`** (M2 결정 2, PRD의 `'[]'`에서 바꿈).
   - **바꾼 이유:** 이사 당일 교체가 흔하다. 앞 세입자가 아침에 나가고 다음 세입자가 그날 들어온다. `'[]'`이면 종료일과 시작일이 같은 날이라 겹친다고 막혀서, 임대인이 날짜를 하루씩 틀리게 적어야 한다.
   - 화면 표기는 시작일 = **"들어오는 날"**, 종료일 = **"나가는 날"**이다. "나가는 날"에는 "이 날 다음 세입자가 들어올 수 있어요"라고 안내한다.
   - 나가는 날은 들어오는 날보다 하루 이상 뒤다(`ck_lease_period`). 그래서 빈 기간은 생기지 않는다.
2. **겹침 차단 = DB 제약 + 서비스 확인 + 호실 잠금**
   - DB: `EXCLUDE USING gist (unit_id WITH =, daterange(start_date, end_date, '[)') WITH &&) WHERE (status = 'ACTIVE')`(V14, btree_gist는 V1). 종료 처리한 계약은 빠진다.
   - 서비스: 저장 전에 같은 규칙으로 확인해 친절한 안내를 띄운다. 안내 문구는 "이 호실에 기간이 겹치는 계약이 있어요. 앞 계약의 나가는 날부터 새 계약을 시작할 수 있어요."이다. 확인 화면에서 한 번, 저장 때 한 번 더 확인한다.
   - **호실 행 잠금(`SELECT ... FOR UPDATE`)**: 등록할 때 먼저 그 호실 행을 잠근다(`PropertyService.lockUnit`, 소유권 확인도 겸함).
     - 동시 등록 테스트에서 처음 드러났다: 잠금 없이 같은 호실에 동시에 넣으면, EXCLUDE 제약 검사끼리 서로의 미확정 행을 기다리다 PostgreSQL이 **교착(deadlock)**을 감지했다. 그래서 한쪽이 "겹침" 대신 잠금 오류로 끝났다.
     - 잠그면 두 번째 요청은 첫 요청이 끝날 때까지 기다린다. 그 뒤 확인 단계에서 첫 계약을 보고 친절한 안내로 끝난다.
     - DB 제약은 마지막 방어선으로 남는다(위반은 제약 이름으로 같은 안내로 바꾼다).
3. **호실 상태와 "현재 계약"** (`UnitOccupancyRule`, ACTIVE 계약만 본다)
   1. 오늘이 기간 안인 계약이 있으면 **입주중**이고, 그 계약이 현재 계약이다(겹침 제약 때문에 많아야 하나).
   2. 없고, 나가는 날이 지난(나가는 날 ≤ 오늘) 계약이 있으면 **기간 지남**이다. 그중 나가는 날이 가장 늦은 계약이 현재 계약이다. 입주 예정 계약이 함께 있어도 기간 지남을 먼저 보여 줘서 종료 처리부터 하게 한다.
   3. 없고, 들어오는 날이 아직 안 온 계약이 있으면 **입주 예정**이다. 가장 빨리 들어오는 계약이 현재 계약이다.
   4. 모두 없으면 **공실**이다.
   - **종료 처리를 잊은 옛 계약 + 새 계약:** 예를 들어 옛 계약의 나가는 날이 10/1인데 종료 처리를 하지 않았고, 10/1부터 새 계약이 시작했다(`[)`라 둘 다 ACTIVE일 수 있다). 이때 상태는 **입주중**, 현재 계약은 **새 계약**이다. 호실 화면에 "나가는 날이 지났는데 종료 처리를 하지 않은 계약이 있어요"라고 함께 안내한다(`staleActive`).
   - 나가는 날 당일은 기간 밖이다. 그날 그 계약만 있으면 상태는 기간 지남(종료 처리 전)이다.
   - 같은 규칙 하나로 건물 목록·건물 상세·호실 화면의 상태를 계산한다(property가 정한 `UnitOccupancy`를 lease가 구현).
4. **월세 이력이 금액의 유일한 기준** (M2 결정 5): lease에는 금액 컬럼이 없다.
   - 어떤 달의 금액은 "그 달 이하에서 가장 최근 `effective_from`"이다. `effective_from`은 청구월이고 그 달 1일로 저장한다(CHECK).
   - 계약을 등록하면 들어오는 달 1일로 첫 행이 생긴다.
   - 이번 달 금액은 이번 달 이하에서 가장 최근 행이다. 아직 들어오기 전 계약이면 첫 행이다. 이번 달 뒤의 행은 "앞으로 바뀌는 금액"으로 따로 보여 준다.
   - 변경 규칙(이번 달 이후·계약 기간 안, 미래 변경의 교체·취소, 이미 시작된 변경은 수정 불가)은 M2 커밋 5에서 구현한다(M2 결정 4).
5. **납부일 1~31**: 입력은 그대로 받는다. 29~31일이면 "그 날이 없는 달은 그 달 마지막 날"이라고 안내한다. 실제 보정 계산은 M3 청구에서 한다.
6. **세입자 재사용** (M2 결정 6): 같은 임대인 안에서 연락처 HMAC이 같으면 같은 세입자다.
   - 확인 화면에서 "이미 등록된 세입자로 계약할까요?"를 묻는다. 동의해야 그 세입자로 계약한다.
   - 이때 새로 입력한 이름·메모로 기존 세입자 정보를 덮어쓰지 않는다.
   - 동시에 같은 번호로 등록되면 UNIQUE 위반을 같은 확인으로 바꾼다.
7. **확인 화면은 세션을 쓰지 않는다:** 입력값을 숨은 칸으로 다시 보내고, 저장할 때 다시 검증한다. 세션은 DB(`spring_session_attributes`)에 평문으로 직렬화되므로 세입자 개인정보를 두지 않는다.

## M3에서 확인할 것 (docs/progress.md "M3 필수 확인")
- `[)`로 같은 날 이어서 입주할 수 있게 되면서, 한 달 안에 세입자가 바뀌는 경우가 더 자주 생긴다. "시작월부터 종료월까지 청구" 기본안이면 그 달 청구가 두 세입자 모두에게 생긴다. 청구 정책에서 푼다.
- 월세 변경 적용월을 "이미 청구가 생긴 달 이후만"으로 강화한다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
|---|---|
| PRD대로 `'[]'` | 이사 당일 교체를 막는다 |
| 서비스 확인만 | 동시 요청을 막지 못한다 |
| DB 제약만 | 오류 안내가 불친절하다. 동시 요청에서 교착이 난다 |
| advisory lock(`pg_advisory_xact_lock`) | 잠금 키 관리가 따로 필요하다. 호실 행 잠금은 소유권 확인과 한 번에 된다 |
| 호실에 상태 컬럼 저장 | 날짜가 지나면 저절로 바뀌어야 해서 배치가 필요하고, 계약과 어긋날 수 있다 |
| lease에 현재 월세 컬럼 | 미래 변경이 있으면 "현재"가 언제 바뀌는지 모호하고, 이력과 어긋날 수 있다 |
